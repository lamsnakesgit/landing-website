# План реализации: Telegram → n8n → безопасный remote coder

## Короткий ответ

Да, это можно сделать.

Но лучший путь — **не открывать полный удалённый терминал из Telegram**, а собрать управляемого агента с очередью задач, approval-гейтами, Git-процессом и изолированным раннером.

---

## 1. Что именно строим

Нужна система из 5 слоёв:

1. **Telegram-интерфейс** — ты пишешь задачу с телефона.
2. **n8n ingress/workflow** — принимает сообщение, нормализует, логирует, создаёт задачу.
3. **Orchestrator/API** — решает, что делать: ответить, спланировать, править код, запускать тесты.
4. **Runner/Agent** — работает с репозиторием в изоляции, делает изменения, гоняет команды.
5. **Git + Audit** — все изменения идут через ветку, diff, лог и подтверждение.

### Рекомендуемая схема

```text
Telegram
   ↓
n8n (webhook + auth + logging + queue)
   ↓
Task API / Orchestrator
   ↓
Sandbox Runner (локальная машина или отдельный VM/контейнер)
   ↓
Git branch + tests + diff + artifact logs
   ↓
Ответ обратно в Telegram
```

## 2. Почему текущий поток с моделью может «вылетать»

Обычно причина в одном или нескольких пунктах:

- слишком длинный контекст в `n8n`;
- потеря состояния между нодами;
- таймауты API или webhook;
- отсутствие retry/backoff;
- нет внешнего хранилища задач и сессий;
- ошибки парсинга JSON/структурированного ответа;
- несколько параллельных сообщений ломают один и тот же state;
- не заложены fallback-маршруты при ошибках модели.

### Что надо включить для диагностики сразу

Для каждого запроса логировать:

- `task_id`
- `telegram_user_id`
- `chat_id`
- `workflow_id`
- `node_name`
- `prompt_version`
- `prompt_hash`
- `model_name`
- `latency_ms`
- `input_size`
- `output_size`
- `retry_count`
- `error_type`
- `error_message`
- `result_status`

### Минимальные меры стабилизации

1. Вынести память/сессии во внешнее хранилище.
2. Добавить `retry` с экспоненциальной задержкой.
3. Поставить таймаут на каждый внешний вызов.
4. Добавить `dead-letter` маршрут для упавших задач.
5. Ввести `idempotency key`, чтобы одно сообщение не запускалось дважды.
6. Версионировать системные промпты.
7. Жёстко валидировать JSON-ответ модели перед следующей нодой.

## 3. Как сделать удалённого кодера правильно

### Базовый принцип

Telegram должен быть **пультом задач**, а не прямой консолью.

То есть пользователь пишет:

> «Исправь баг в auth, прогони тесты, покажи diff»

А система делает так:

1. создаёт задачу;
2. понимает тип запроса;
3. строит план;
4. просит подтверждение, если риск выше безопасного порога;
5. запускает раннер в изоляции;
6. коммитит изменения в отдельную ветку;
7. возвращает результат, лог и diff.

---

## 4. Режимы доступа

### Режим A — Planner only

Безопасный старт:

- агент читает репозиторий;
- отвечает, что собирается сделать;
- ничего не меняет без подтверждения.

### Режим B — Patch mode

- агент может менять файлы;
- работает только в feature-ветке;
- не пушит в `main`;
- обязательно возвращает diff и summary.

### Режим C — Test mode

- может запускать только команды из allowlist;
- например `npm test`, `pnpm lint`, `pytest`, `git diff`.

### Режим D — Dangerous ops

Только вручную и отдельно:

- миграции БД;
- деплой;
- изменение секретов;
- установка новых зависимостей;
- команды удаления;
- любые сетевые операции вне allowlist.

## 5. Безопасная архитектура

## 5.1 Аутентификация

- allowlist по `telegram_user_id`;
- отдельный secret на webhook;
- одноразовые approval-токены для опасных действий;
- необязательный PIN/пароль на подтверждение действий.

## 5.2 Авторизация

Роли:

- **owner** — полный контроль;
- **reviewer** — может approve/reject;
- **viewer** — только смотреть статус, diff, логи.

## 5.3 Изоляция выполнения

Лучше всего:

- отдельный runner на VM/мини-сервере;
- контейнер/изолированная рабочая директория на задачу;
- монтируется только нужный репозиторий;
- временная файловая система, где это возможно.

Если запускать на своей машине, то всё равно:

- только выделенная папка для разрешённых репозиториев;
- отдельный системный пользователь;
- без доступа ко всему домашнему каталогу;
- без прямого доступа к глобальным SSH-ключам, если можно избежать.

## 5.4 Git safety

- одна задача = одна ветка;
- прямой push в protected branch запрещён;
- все изменения через diff;
- автокоммит только в task branch;
- обязательный rollback / discard задачи.

## 5.5 Command allowlist

Разрешать только команды из белого списка, например:

- `git status`
- `git diff`
- `git checkout -b <task-branch>`
- `npm test`
- `pnpm lint`
- `pytest`
- `ruff check`
- `tsc --noEmit`

Запрещать по умолчанию:

- `rm -rf`
- `curl ... | sh`
- `sudo ...`
- произвольные `ssh`/`scp`
- изменение system config
- запуск неизвестных бинарников

## 5.6 Секреты

- секреты хранятся вне промптов;
- модель не получает сырые `.env`, токены и ключи без крайней необходимости;
- в логах — редактирование/маскирование секретов;
- runner получает только минимально нужные креды.

## 5.7 Kill switch

Обязательно нужна команда:

- `/stop TASK_ID`

Она должна:

- останавливать текущий процесс;
- отзывать активный approval;
- помечать задачу как aborted;
- сохранять журнал того, что уже успело произойти.

---

## 6. Важная правда про «подписку GPT»

Если ты имеешь в виду обычную пользовательскую подписку в приложении/вебе, то **как правило это не равно API-доступу**.

Для такой системы обычно нужен **отдельный API-ключ и отдельный биллинг API**.

Поэтому архитектуру лучше строить так, чтобы слой модели был абстрактным:

- `LLM Adapter`
- можно менять модель без переписывания всего пайплайна;
- fallback на вторую модель при деградации первой;
- централизованное логирование стоимости, времени и ошибок.

## 7. Что я рекомендую как лучший вариант

### Вариант 1 — Быстрый старт

`Telegram → n8n → LLM → ответ`

Подходит только для:

- Q&A;
- простого планирования;
- текстовых задач;
- без реального кодинга.

### Вариант 2 — Практичный прод-скелет

`Telegram → n8n → Task API → Runner → Git`

Это мой рекомендуемый вариант.

Плюсы:

- надёжнее;
- легче логировать;
- легче останавливать;
- можно дозировать права;
- можно развивать от planner к полноценному coder.

### Вариант 3 — Максимально безопасный

То же самое, но runner живёт не на основной машине, а на отдельном сервере/VM.

Это лучший вариант, если:

- много репозиториев;
- есть прод-секреты;
- не хочешь рисковать личной машиной.

## 8. Пошаговый план внедрения

### Фаза 1 — Диагностика текущего `n8n`

Сделать:

- собрать текущий workflow;
- включить структурированные логи;
- пометить точки падения;
- зафиксировать таймауты, payload size и ошибки;
- вынести session state наружу.

Результат:

- будет ясно, почему текущий ассистент тупит и где именно ломается.

### Фаза 2 — Безопасный planner в Telegram

Сделать:

- команды `/new`, `/plan`, `/status`, `/stop`;
- создание `task_id`;
- очередь задач;
- ответы с plan/risk summary.

Результат:

- уже можно ставить задачи с телефона без опасного shell-доступа.

### Фаза 3 — Patch + branch + diff

Сделать:

- runner для работы с Git;
- ветка на задачу;
- генерация patch/diff;
- возврат артефактов обратно в Telegram.

Результат:

- агент реально правит код, но безопасно и прозрачно.

### Фаза 4 — Тесты и проверка качества

Сделать:

- allowlist команд;
- лимиты времени и ресурсов;
- сбор stdout/stderr;
- сводка по тестам.

Результат:

- агент может не только править, но и проверять, что не сломал проект.

### Фаза 5 — Approve / Reject / Merge

Сделать:

- ручное подтверждение рискованных действий;
- merge только после approve;
- auto-close/revert задачи.

Результат:

- получается управляемый удалённый кодер, а не «бот с полной властью».

## 10. Итоговая рекомендация

Да, твоя идея реалистична.

Самый правильный путь — строить **не “удалённый терминал в Telegram”**, а **безопасного удалённого coding-agent'а** с такими свойствами:

- задачи приходят из Telegram;
- orchestration делает `n8n`;
- выполнение идёт в sandbox runner;
- все изменения через Git-ветку;
- опасные операции только через approve;
- всё логируется и можно остановить в любой момент.

Это как раз тот вариант, который может быть похож по ощущению на remote coding assistant, но заметно безопаснее и управляемее.

## 12. Что находится в приложенном гайде

Приложенный PDF — это **не n8n workflow**, а архитектурный гайд по сборке ассистента на:

- `Next.js`;

- `Supabase`;

То есть в гайде ассистент построен не как набор нод `n8n`, а как собственный backend с модулями:

- база сообщений;
- history/context;
- tool calling;
- отправка сообщений;
- напоминания;
- поиск;
- ежедневный отчёт.

### Почему это всё равно полезно

Этот гайд можно использовать как **референс для логики ассистента**, а `n8n` — как слой orchestration.

Проще говоря:

- саму бизнес-логику можно перенести в `n8n`;
- часть можно вынести в отдельный API/runner;
- tool-use сценарии из гайда хорошо ложатся на будущий coding-agent flow.

## 13. Как я бы сделал копию ассистента безопасно

### Главный принцип

**Основной ассистент не трогаем напрямую.**

Делаем отдельную копию, условно:

- `assistant-main` — текущий рабочий ассистент;
- `assistant-coder-copy` — экспериментальная ветка/копия для coding-agent функций.

### Что значит «основной только читать»

Я трактую это так:

- основной workflow не меняется автоматически агентом;
- основной workflow не получает опасные coding-tools;
- копия может читать нужные данные/контекст;
- все эксперименты, новые команды и risky steps идут только в копии.

### Практическая схема

#### Main workflow

Оставляем в роли production-reader / user-facing assistant:

- принимает обычные сообщения;
- может показывать статус задач;
- может читать summary, diff, лог из копии;
- не запускает опасные операции по коду.

#### Copy workflow

Новая копия получает команды типа:

- `/code`
- `/plan`
- `/patch`
- `/test`
- `/diff`
- `/approve`
- `/stop`

Именно copy workflow:

- создаёт `task_id`;
- строит план;
- решает, нужен ли approve;
- отправляет задачу во внешний runner;
- возвращает diff, статус и summary.

## 14. Как «прикрутить Cline-подобное поведение» правильно

Если говорить честно, Cline-подобный режим — это не просто одна нода LLM.

Нужны минимум 4 слоя:

1. **Planner** — понимает задачу и строит пошаговый план.
2. **Repo Reader** — читает проект, файлы, структуру, diff.
3. **Patch Executor** — создаёт изменения, но только в sandbox/ветке.
4. **Verifier** — запускает allowlist-команды: тесты, линтеры, typecheck.

### В `n8n` это лучше делить так

`n8n` отвечает за:

- приём команды из Telegram;
- маршрутизацию;
- очередь;
- approvals;
- статус задач;
- отправку результатов обратно.

Внешний runner/API отвечает за:

- чтение репозитория;
- изменение файлов;
- git branch;
- запуск тестов;
- сбор артефактов.

### Почему не стоит кодить прямо внутри n8n

Потому что `n8n` хорош как оркестратор, но не как полноценная среда для безопасного file-edit + repo-ops + test execution.

Поэтому лучший вариант — **n8n сверху, runner снизу**.

## 15. Минимальная безопасная версия копии

### Этап 1 — Planner-only copy

Копия умеет:

- принять задачу;
- разложить на план;
- оценить риск;
- попросить approve;
- ничего не менять в коде.

Это уже полезно и почти безопасно.

### Этап 2 — Read repo + diff proposal

Копия умеет:

- читать разрешённый репозиторий;
- искать файлы;
- предлагать patch;
- показывать diff;
- не применять изменения без approve.

### Этап 3 — Controlled patch mode

Копия умеет:

- вносить изменения только в отдельной ветке;
- запускать только разрешённые команды;
- возвращать артефакты в Telegram.
