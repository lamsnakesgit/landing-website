# Walkthrough: как это будет работать с телефона

## 1. Пользовательский сценарий

Ты пишешь в Telegram, например:

```text
/new Исправь баг в авторизации в repo X, прогони тесты и покажи diff
```

Система отвечает:

```text
TASK-248 создан.

План:
1. Проверить модуль auth
2. Найти точку падения
3. Подготовить patch
4. Прогнать разрешённые тесты
5. Вернуть diff

Риск: medium
Требуется approve на изменение файлов: да
```

Ты подтверждаешь:

```text
/approve TASK-248
```

После этого раннер:

1. клонирует/открывает разрешённый репозиторий;
2. создаёт ветку `task/TASK-248-auth-fix`;
3. вносит изменения;
4. гоняет тесты из allowlist;
5. собирает diff и лог;
6. отправляет результат обратно в Telegram.

---

## 2. Команды, которые стоит поддержать

### Основные

- `/new <описание>` — создать задачу
- `/plan <task_id>` — показать план
- `/status <task_id>` — показать текущий статус
- `/approve <task_id>` — разрешить следующий рискованный шаг
- `/reject <task_id>` — отклонить задачу
- `/stop <task_id>` — аварийно остановить задачу
- `/diff <task_id>` — показать diff
- `/logs <task_id>` — показать лог выполнения

### Полезные

- `/tasks` — список последних задач
- `/retry <task_id>` — повторить безопасный этап
- `/summary <task_id>` — короткая сводка результата

---

## 3. Как должен выглядеть жизненный цикл задачи

### Состояния

```text
created
queued
planning
awaiting_approval
running
testing
completed
failed
aborted
```

### Хороший принцип

Любой переход состояния должен логироваться с временем и причиной.

Например:

- `queued → planning`
- `planning → awaiting_approval`
- `awaiting_approval → running`
- `running → testing`
- `testing → completed`

---

## 4. Как не превратить это в дыру по безопасности

## Нельзя

- давать боту выполнять любой shell-ввод как есть;
- разрешать работу во всех каталогах машины;
- хранить секреты прямо в n8n-нодах и промптах;
- разрешать деплой и destructive ops из одного Telegram-сообщения.

## Нужно

- список разрешённых пользователей;
- список разрешённых репозиториев;
- список разрешённых команд;
- отдельный approval на рискованные действия;
- изоляция раннера;
- журнал всех действий;
- kill switch.

## 5. Как диагностировать текущего ассистента в `n8n`

Вот минимальный практический чеклист:

1. Поставить `task_id` в самое начало workflow.
2. Прокинуть `task_id` через все ноды.
3. Сохранять вход/выход каждой критичной ноды.
4. Отдельно логировать ошибки API и таймауты.
5. Проверить, не ломается ли workflow на JSON parsing.
6. Проверить, не теряется ли история между сообщениями.
7. Проверить параллельные апдейты из Telegram.
8. Добавить fallback, если модель вернула мусор или пустой ответ.

Если сделать только эти 8 пунктов, уже станет гораздо яснее, почему текущая схема нестабильна.

## 6. Практичный MVP, который реально стоит собирать первым

### MVP-1

- Telegram принимает задачу
- `n8n` создаёт `task_id`
- агент строит план
- пользователь делает approve
- агент подготавливает patch
- агент возвращает diff

Без автодеплоя. Без опасных команд. Без прямого shell.

### MVP-2

- добавить запуск тестов
- добавить ветки и коммиты
- добавить список задач и историю

### MVP-3

- отдельный runner на VM
- ограничения по repo/branch/command
- политики approve по типу изменений

---

## 7. Самая здравая итоговая модель

Если коротко, тебе нужен не просто «бот с моделью», а вот это:

- **Telegram** — интерфейс управления;
- **n8n** — маршрутизация, логика, очереди, webhooks;
- **LLM** — планирование, анализ, генерация патчей;
- **Runner** — безопасное выполнение действий по коду;
- **Git** — контроль изменений;
- **Approve layer** — защита от опасных действий.

Тогда ты реально сможешь с телефона писать задачи вроде:

> «Почини тесты в репе A, не трогай зависимости, покажи diff»

И система будет делать это предсказуемо, не превращаясь в неконтролируемый удалённый shell.

---

## 8. Что логично делать следующим шагом

Следующий практический шаг — выбрать один из двух путей:

1. **Диагностируем текущий workflow `n8n`** и лечим нестабильность.
2. **Сразу проектируем MVP remote coder**: Telegram-команды, Task API, runner и approve flow.

Оба пути нормальные, но я бы начал с диагностики текущего пайплайна, чтобы не переносить старые проблемы в новую систему.

## 9. Как должна выглядеть схема с копией ассистента

### Что есть сейчас

- есть основной ассистент;
- есть намёк на использование `n8n-as-code`;
- но нет локального экспортированного workflow.

### Что делаем дальше

#### Вариант структуры

```text
Telegram
  ├─> main assistant (read-only / stable)
  └─> coder copy (experimental / approvals / patch / diff)
```

### Обязанности main assistant

- обычное общение;
- чтение статуса задач;
- чтение summary/diff;
- никаких опасных действий по коду.

### Обязанности coder copy

- приём команд на кодинг;
- планирование;
- выдача risk summary;
- запрос approve;
- работа с runner;
- возврат результата.

### Почему это правильно

Если coder-copy сломается, основной ассистент не падает.

Это и есть правильный способ делать эволюцию: не мутировать production-flow, а выращивать отдельную экспериментальную ветку.
