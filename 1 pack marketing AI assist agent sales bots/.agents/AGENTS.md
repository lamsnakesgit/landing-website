- **ПРАВИЛЬНО**:
  1. Создать файл локально через `write_to_file`

## n8n HTTP Request Tool для AI-Агентов
- **Строгая типизация данных**: При создании HTTP Request тула для AI агента, если стороннее API (например, OpenAI, GRSAI) требует передачи **чисел** (integer/float) или **булевых** значений (boolean), КАТЕГОРИЧЕСКИ ЗАПРЕЩАЕТСЯ использовать стандартные поля "Body Parameters" (потому что n8n по умолчанию передаёт их как строки, что вызывает ошибку `Parameter data type error`).
- **Как чинить**: Нужно переключить `specifyBody` на `json` и прописать сырой код, используя `$fromAI` для промпта: 
  `={{ JSON.stringify({ "model": "...", "prompt": $fromAI("query", "Описание", "string"), "n": 1 }) }}`

## n8n Управление нодами (Удаление / Деактивация)
- **Конфликт тулов**: Если у AI-агента подключено несколько одинаковых по смыслу инструментов (например, три разных image-генератора), агент будет путаться и может вызывать отключенные ноды.
- **ЗАПРЕТ НА УДАЛЕНИЕ**: КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО удалять ноды (удалять их полностью из JSON-структуры `nodes`) без явного разрешения пользователя!
- **Как чинить**: Если нужно убрать тул из поля зрения агента, необходимо ТОЛЬКО **отключать связь** (убирать соединение из объекта `connections`) или **деактивировать** ноду (ставить `disabled: true`). Сама нода обязана остаться на холсте воркфлоу.

## Строгое правило: Версионирование (Git Commits)
- **ОБЯЗАТЕЛЬНЫЕ коммиты**: После каждого изменения логики, создания новых воркфлоу или редактирования JSON, агент ОБЯЗАН делать коммит изменений через git (`git add .` и `git commit`).
- **Частота**: Рекомендуется делать коммиты каждые 5-10 минут во время активной работы.
- Это правило строго обязательно для всех агентов во всех проектах. Нельзя оставлять завершенные задачи незакоммиченными.

## Google Cloud API & n8n HTTP Request Troubleshooting
- **TTS и 403 Forbidden**: Если n8n выдает ошибку `403 Forbidden` (unregistered callers) при работе с Google Cloud TTS через Service Account, это баг n8n с передачей OAuth Scopes.
- **Решение**: НЕ использовать Service Account (JSON). Вместо этого сгенерировать сырой API Key в консоли Google Cloud (раздел Credentials), отключить Authentication (поставить None) в ноде n8n, и приклеить ключ к URL: `https://texttospeech.googleapis.com/v1beta1/text:synthesize?key=ТВОЙ_КЛЮЧ`.
- **Vertex AI (Gemini)**: В отличие от TTS, Vertex AI работает **только** через Service Account (JSON). Использовать обычный API Key для него нельзя.

# Rule: 01-language-and-style.md
# Язык и базовое поведение агента

## Язык
- Всегда отвечай пользователю на русском, если он пишет на русском.
- Все комментарии и docstrings в коде пиши на русском.
- Имена переменных, функций, классов и файлов оставляй на английском.

## Честность и достоверность
- Не выдумывай факты, файлы, API, результаты тестов, ошибки или якобы выполненную работу.
- Не сообщай, что задача завершена, если она не завершена.
- Не выдавай предположения, планы или намерения за проверенный результат.
- Если что-то не проверено, недоступно или не получилось, говори об этом прямо.
- Если собственных знаний недостаточно, информация version-sensitive или есть риск ошибки, добирай достоверность через локальный код, доступные MCP, официальную документацию и поисковые инструменты.
- Для актуальной внешней информации и best practices используй доступные инструменты поиска, включая Tavily и Exa.
- Если нужна готовая реализация или надёжный паттерн, ищи готовые решения, примеры и части решений в документации и реальных репозиториях.
- Не выдавай найденную через поиск или MCP информацию за внутреннее знание модели.

## Коммуникация
- Пиши кратко, по делу и без лишней теории.
- Объясняй технические вещи простым языком.
- Для нетривиальных задач сначала коротко обозначай логику действий.
- Не отвечай пустыми, расплывчатыми или маскирующими незнание формулировками.

## Формат отчётов и аудитов
- Для audit/read-only review, research summary, postmortem, compare и status-update ответов используй аккуратный Markdown-формат, а не длинные сплошные абзацы.
- Если пользователь просит подробный отчёт или если задача завершилась реальной проверкой/деплоем/smoke-test, по умолчанию давай более подробный и предметный отчёт, а не только короткое резюме.
- Для таких подробных отчётов предпочитай явную структуру: `Короткий вывод` → `Что проверено` → `Подробно по подтверждённым пунктам` → `Что изменено` → `Что осталось / next step`.
- Если есть конкретные сущности, ID, URL, env-флаги, metadata-поля, модели, latency или статусы — перечисляй их явно отдельными bullets, чтобы отчёт можно было использовать как готовый handoff/result note.
- По умолчанию строй такие ответы в структуре: `Короткий вывод` → `Что проверено` → `Ключевые находки` → `Риски / gaps` → `Что рекомендую дальше`.
- Для списка находок, рисков и рекомендаций предпочитай bullets или нумерованные списки; для сравнения допускаются таблицы.
- Если выводов много, сначала дай 3–6 самых важных пунктов вверху, а потом детали ниже.
- Не превращай отчёт в полотно текста: одна мысль = один абзац или один bullet.
- Если результат основан на реальной проверке, отделяй `что подтверждено` от `что выглядит вероятным, но требует проверки`.
- Для нетривиальных отчётов используй ясные заголовки, короткие секции и визуально читаемый ритм текста.

## Инженерное поведение
- Предпочитай простые, надёжные и проверяемые решения вместо хрупких и переусложнённых.
- Сначала понимай существующую систему, потом предлагай изменения.
- При отладке сначала ищи корневую причину, потом исправляй последствия.
- Комментарии должны объяснять смысл, допущение или нестандартное решение, а не очевидное.

## Неоднозначность и допущения
- Если неоднозначность влияет на безопасность, точность, необратимость или ожидаемый результат, сначала уточни запрос.
- Если риск низкий и можно сделать разумное инженерное допущение, действуй самостоятельно.
- Важные допущения фиксируй явно и кратко.

## Приоритет инструкций
- Безопасность и честность важнее стилистических предпочтений.
- Project и workspace rules важнее global rules.
- Более узкие и специализированные rules важнее общих, если они не противоречат безопасности и честности.


# Rule: 02-documentation-search.md
# Поиск документации и готовых решений

## Когда поиск обязателен
- Если знаний недостаточно для точного ответа или безопасного действия — ищи.
- Если информация version-sensitive, зависит от текущего API, CLI, SDK, модели или провайдера — ищи.
- Если локальный код и документация проекта не дают уверенного ответа — ищи.
- Если нужна готовая реализация, production pattern или best practice — ищи не только документацию, но и реальные примеры.

## Порядок поиска
- Для repo-specific задач сначала изучай локальный проект: README, docs, package.json, pyproject.toml, конфиги и существующий код.
- Для внешних библиотек, API, SDK, CLI и фреймворков сначала используй официальную документацию и официальные руководства.
- Если official docs не покрывают edge-case, используй changelog, issues, discussions и технические статьи.
- Community-источники используй как слой workaround’ов и спорных кейсов, а не как основной источник истины, если есть official source.

## Выбор инструмента
- Используй локальный код и доступные MCP раньше веб-поиска, если ответ может быть внутри проекта или подключённых систем.
- Для документации библиотек и фреймворков предпочитай Context7, если он доступен.
- Используй Tavily для актуальной внешней информации, best practices, changelog, свежих API и нестандартных ошибок.
- Используй Exa для чистого контента, semantic search, code examples и поиска качественных технических материалов.
- Если нужен готовый production pattern, используй GitHub MCP и поиск по репозиториям/коду.
- Для задач на готовые реализации, mature patterns и production-grade примеры используй skill `implementation-research`.

## Поиск ошибок и реализаций
- Ошибки ищи по точному error string, stack trace, коду ответа или симптому.
- Если нужна реализация, ищи canonical example, official guide, готовые snippets и части решений в реальных репозиториях.
- Не изобретай решение с нуля, если уже существует проверяемый и уместный паттерн.
- При выборе примеров предпочитай зрелые и понятные реализации, а не случайные сниппеты без контекста.

## Прозрачность источников
- Явно указывай, на каких источниках основано решение.
- Не выдавай найденную через поиск, MCP или репозитории информацию за внутреннее знание модели.
- Если источник неофициальный, обозначай это прямо.
- Если уверенность ограничена или данные противоречат друг другу, фиксируй это в ответе.


# Rule: 03-context-memory-bank.md
# Context Management & Memory Bank

## Управление контекстом
- Следи за чистотой контекста: длинная и нерелевантная история ухудшает качество решений.
- Используй `/smol` (alias: `/compact`), если нужно сжать текущую задачу без смены контекста работы.
- Используй `/newtask`, если задача сменилась, контекст перегружен или нужен чистый handoff.
- Auto-Compact считай фоновой страховкой, а не заменой осмысленного управления памятью.
- Если видишь `context usage` / `context window progress` / progress bar около `70%`, считай это ранним порогом compaction.
- Если видишь `context usage` / `context window progress` / progress bar около `90%`, считай это критическим порогом и приоритетом для срочного compaction.

## Пороги compaction
- `70%` — ранний порог compaction.
- `90%` — критический аварийный порог.

## Поведение на 70%
- Перед крупным чтением, широким поиском, grep, build, test run, рефакторингом или multi-file edit сначала инициируй `/smol` / `/compact`.
- После compaction продолжай только с минимального следующего полезного шага.
- Предпочитай узкие чтения файлов, точечный поиск и инкрементальные правки.
- Не подтягивай большие логи и большие сгенерированные файлы без строгой необходимости.

## Поведение на 90%
- Немедленно останавливай несущественную работу.
- Срочно инициируй `/smol` / `/compact` до любых следующих тяжёлых действий.
- Не запускай heavy commands, broad scans, длинные тестовые прогоны и большие чтения файлов до compaction.
- Не продолжай обычное выполнение задачи, пока compaction не завершён.

## Если compaction не помог
- Если контекст остаётся высоким после compaction или задача меняет фазу, используй `/newtask`.
- В handoff переноси только: текущую цель, уже принятые решения, изменённые файлы, оставшиеся следующие шаги и blockers / risks.
- Не тащи в новый task шумные логи, тупиковые попытки и дублирующуюся историю.

## Project identity in continuity
- В первом содержательном ответе нового task, resume, compaction-recovery или handoff MUST явно указывать текущий проект строкой `Проект: <workspace-rule-file.md>` или `Проект: <project-name>`, а следующей строкой — текстовый progress bar в формате Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Если в workspace есть `.clinerules/{project-name}.md`, его имя файла SHOULD быть каноническим project label для статусов, handoff и continuity-ответов.
- Если workspace rule ещё не создан, MUST явно предложить создать его и до этого использовать временный project label в том же формате.
- `implementation_plan.md`, `cline_docs/project-state.md`, `cline_docs/handoff-summary.md` и аналогичные continuity-файлы SHOULD начинаться с блока из двух строк: сначала `Проект: ...`, затем `Завершённость: [███████████░░░] 80% — <короткая фаза>`, чтобы после compaction/resume было сразу видно, над чем идёт работа и где мы по прогрессу.

## Project progress bar standard
- Канонический визуальный формат после строки `Проект: ...` = Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Процент может быть приблизительным инженерным ориентиром, а не псевдо-точной метрикой; он должен честно отражать стадию проекта.
- Короткая фаза после процента должна описывать текущий этап в 2–5 словах: например `runtime integration`, `regression`, `handoff cleanup`, `planning`.
- Если проект только начат, допустимы низкие значения вроде `10–20%`; если идёт финализация, допустимы `80–95%`; не ставить `100%`, пока definition of done реально не закрыт.

## Project State
- Если существует `cline_docs/handoff-summary.md`, читай его сразу после `cline_docs/project-state.md`, особенно после compaction / resume / handoff.
- Для длинных задач `handoff-summary.md` SHOULD хранить короткую resume-выжимку: что уже подтверждено, где остановились, следующий точный шаг и важные operational notes.
- После compaction или восстановления сессии сначала перечитывай `project-state.md` + `handoff-summary.md`, а уже потом продолжай execution.
- Если существует `cline_docs/project-state.md`, используй его как оперативную выжимку по текущей задаче.
- Для длинных задач `cline_docs/project-state.md` SHOULD хранить: текущую фазу, уже сделано, следующий точный шаг, modified files, ключевые решения и risks/blockers.
- Если в проекте есть `implementation_plan.md` или аналогичный plan file, читай его вместе с `cline_docs/project-state.md`: plan file = master plan, project-state = оперативное состояние.
- При handoff, resume и compaction source of truth для long-task continuity = `implementation_plan.md` + `cline_docs/project-state.md`, а не только Focus Chain или память текущего task.
- Обновляй `project-state.md` после значимого прогресса, перед compaction и перед передачей задачи.
- Не обновляй state-файл бюрократически после каждого мелкого действия.

## Checkpoints и краткость
- Для длинных execution-задач предпочитай короткие, проверяемые slices вместо одной большой непрозрачной фазы.
- После каждого значимого slice SHOULD обновлять `cline_docs/project-state.md` и, если есть, `cline_docs/handoff-summary.md`, чтобы следующий resume не зависел от памяти текущего чата.
- Checkpoints сохраняют состояние кода; Memory Bank и project-state сохраняют знания и контекст.
- Если задача ушла в серию неудачных итераций или накопила много нерелевантной истории, предпочитай сжатие или новую задачу вместо раздувания текущей сессии.
- Держи memory-файлы короткими, конкретными и ориентированными на продолжение работы.

## Границы правила
- Это правило управляет памятью и контекстом, а не процессом разработки.
- Логику разбиения задач, подтверждений пользователя, workflow-шагов и commit cadence держи в отдельных process/workflow rules.


# Rule: 04-web-development.md
# Разработка сайтов и приложений

## Локализация интерфейса
- Все сайты и приложения должны иметь интерфейс на русском языке по умолчанию.
- Все пользовательские тексты: кнопки, меню, формы, сообщения, заголовки и подсказки — на русском.
- Учитывай падежи, множественное число, длину строк, формат дат, чисел и полей ввода.
- Не смешивай русский интерфейс с англоязычными подписями, placeholder’ами и системными сообщениями без явной причины.

## UX и доступность
- Интерфейс должен быть понятным, предсказуемым и доступным.
- Используй семантическую разметку, явные заголовки, подписи к полям и понятные состояния элементов.
- Формы должны быть короткими, иметь labels, валидацию и ясные сообщения об ошибках на русском языке.
- Не полагайся только на цвет для передачи статуса, ошибки или успеха.
- Обеспечивай базовую клавиатурную доступность и понятный порядок взаимодействия.
- Предпочитай нативные HTML-контролы; кастомные виджеты делай только когда это действительно нужно, и тогда опирайся на проверенные accessible patterns (`WAI-ARIA APG`, Radix, mature design systems), а не на самодельную клавиатурную логику.
- Для нетривиального UI проектируй не только happy path, но и ключевые состояния: `loading`, `empty`, `no results`, `error`, `success/confirmation`, `disabled`, `permission`, `first-use`.
- Для форм ошибки и успех должны быть заметны и текстом, и визуально: сообщение рядом с полем или в summary-блоке, явный способ понять что сломалось и как исправить.
- Не делай критичный UX зависящим только от hover, и не используй мигающий/автозапускающийся контент без явного контроля пользователя.

## Адаптивность и производительность
- Проектируй интерфейс адаптивно и учитывай основные сценарии на мобильных и широких экранах.
- Предпочитай лёгкие и быстрые интерфейсы вместо тяжёлых визуальных решений без пользы.
- Сохраняй чистую информационную архитектуру, короткие пользовательские сценарии и минимально необходимое количество действий.
- Считай responsive-поведение свойством компонента, а не только страницы: кнопка, таблица, форма, карточка и модалка должны корректно жить в разных контейнерах и брейкпоинтах.
- Проверяй интерфейс не только по ширинам экранов, но и при увеличении масштаба; не запрещай zoom и не ломай layout при 200–400%.

## Контент и продуктовая чистота
- Не добавляй в пользовательский интерфейс названия провайдеров, тарифы, цены, контакты провайдеров и рекламные блоки, если пользователь явно этого не просил.
- Фокусируйся на функциональности, ясности интерфейса и пользовательской задаче.
- Не перегружай интерфейс декоративными, маркетинговыми или отвлекающими элементами без продуктовой пользы.

## Структура и недостающие требования
- Используй семантические HTML-элементы и понятную структуру интерфейса вместо хрупких несемантических паттернов.
- Если входной документации недостаточно, уточняй требования к дизайну, целевой аудитории, ключевым сценариям, must-have функциям, API/интеграциям, адаптивности, доступности и производительности.
- Если риск низкий, делай нейтральные UX-допущения и явно фиксируй их.
- Держи source order в DOM согласованным с визуальным порядком; не переставляй смысловые блоки только CSS-ом так, чтобы tab order становился нелогичным.
- Используй постоянные видимые labels; placeholder не заменяет label и не должен хранить критичную инструкцию.
- Для touch-сценариев делай достаточно крупные цели касания; по умолчанию ориентируйся на ~44×44px для важных интерактивных элементов.
- Пустые состояния должны заменять отсутствующий контентный контейнер, а не оставлять пользователю пустые таблицы, заголовки или шумные обвязки без данных.
- Для нетривиальных UI/frontend задач MUST сначала проверить релевантный UI skill и загрузить его через `use_skill()`, а уже потом проектировать или писать UI.
- `frontend-design` используй для React/Tailwind product UI и обычной frontend-реализации.
- `cc-design` используй для HTML-first high-fidelity прототипов, интерактивных design demo, HTML-слайдов, landing page mockups, wireframes и design-system explorations.
- `huashu-design` используй для HTML-first high-fidelity прототипов, анимаций, visual variation exploration, design-direction advisor сценариев и задач с экспортом MP4/GIF/PPTX.
- Если пользователь именно **планирует UI** или просит помочь с визуальным направлением, routing к этим skills всё равно обязателен до начала содержательной UI-работы.
- Если нужен референсный UI, best practice или готовый паттерн, ищи лучшие кейсы через official docs, Exa, Tavily и зрелые репозитории, а не придумывай визуальные решения с нуля.

# Правила использования инструментов поиска

## Таблица: задача → инструмент

|---|---|

## Базовый research priority
- Для внешнего исследования по умолчанию используй связку: **Tavily → Exa → Context7 → GitHub MCP**.
- Для library/framework документации Context7 может подниматься выше общего research-потока.
- Если ответ может уже быть в проекте или доступных MCP, сначала используй локальный код и внутренние инструменты.

## Автоматическое применение
- Новая технология или сервис → сначала `tavily_search`/`tavily_research`, потом `web_search_exa`, затем official docs и repo patterns.
- Баг/ошибка → `tavily_search` (advanced) + exact error search + official docs/issues.
- Анализ чужого сайта → `tavily_extract` + `tavily_map`.
- Чистый контент без мусора → `web_search_exa`.
- Сниппеты кода, SDK usage и примеры → `get_code_context_exa`.
- Документация библиотек → `context7` (приоритет над памятью модели).
- Готовые реализации и production patterns → `github search_code`, `github search_repositories`, skill `implementation-research`.
- Локальный поиск по большой кодовой базе → `cocoindex-code → search`, skill `local-code-search`.
- Нетривиальные UI/frontend референсы → сначала official accessibility/pattern docs (`W3C WAI`, `ARIA APG`, `web.dev`, mature design systems вроде `USWDS` / `Carbon` / `Primer` / `Material`), затем skill `frontend-design` / `cc-design` / `huashu-design`, потом Exa/Tavily и зрелые репозитории.

## Несколько проходов поиска
- Если после первого поиска ответ остаётся неполным, противоречивым или слабым, делай второй и третий проход через Tavily, Exa, Context7 и GitHub MCP.
- Используй несколько поисковых проходов для задач, где важны качество решения, свежесть API, зрелые паттерны или высокая цена ошибки.
- Не останавливайся на одном источнике, если нужен production-grade результат.

## Official-first routing
- Для сервиса, SDK, API, провайдера или фреймворка сначала ищи официальный сайт, официальный docs URL, официальный GitHub-репозиторий и first-party материалы.
- Если официальный источник найден, используй его как базовую точку истины.
- Вторичные статьи, блоги и community-материалы используй только после first-party источников или для edge-cases.
- Для UI/accessibility задач first-party слоем по умолчанию считаются `W3C/WAI`, `ARIA APG`, `web.dev` и официальные design-system docs используемого стека или паттерна.

## Skills и search routing
- Для задач на готовые реализации, mature patterns и production-grade примеры используй skill `implementation-research`.
- Для поиска реализаций внутри локального репозитория используй skill `local-code-search`.
- Для нетривиальных UI/frontend задач и поиска лучших UI-кейсов используй skill `frontend-design`; для general HTML-first high-fidelity design/prototype задач используй `cc-design`; для HTML-first design demo, motion/animation, export-heavy и design-variation/design-direction задач используй `huashu-design`.
- Для форм, accessibility, keyboard/focus behavior и custom widgets сначала добирай official guidance (`WAI`, `APG`, `web.dev`, `design-system docs`), и только потом адаптируй найденный паттерн под текущий стек.

## Context7 — приоритет
- MUST автоматически вызывать `resolve-library-id` → `query-docs` при генерации кода для конкретных библиотек.
- MUST предпочитать данные из Context7 обучающим данным модели.


# Rule: 06-code-quality.md
# Правила качества кода

## Перед написанием кода
- Сначала изучай существующую кодовую базу, паттерны и структуру проекта.
- Не дублируй существующую логику, если её можно переиспользовать.
- Проверяй совместимость решения с текущим стеком, архитектурой и соглашениями проекта.
- Предпочитай читаемость и простоту избыточной изобретательности.
- Вноси минимальные, безопасные и reviewable изменения.
- Избегай лишних зависимостей без явной пользы.

## Ошибки и валидация
- Внешние вызовы должны иметь контролируемую обработку ошибок в соответствии с языком и архитектурой проекта.
- Логируй ошибки с полезным контекстом, но без утечки секретов и чувствительных данных.
- Возвращай понятные сообщения об ошибках и предсказуемое поведение на failure-path.
- Валидируй входные данные на границах системы.

## Безопасность по умолчанию
- Никогда не хардкодь секреты, ключи, токены и пароли в коде.
- Используй переменные окружения, secret managers или безопасные конфиги.
- Не передавай секреты через MCP и внешние инструменты без явной необходимости.
- Предпочитай безопасные настройки по умолчанию, принцип наименьших привилегий и проверенные зависимости.
- Проверяй новые зависимости и внешние интеграции на необходимость, репутацию и риски.

## Проверка результата
- После изменений проверяй результат через доступные механизмы: тесты, линтеры, сборку, браузер, CLI или воспроизведение сценария.
- Если меняется поведение, API или архитектура, обновляй связанную документацию и проверяй зависимые места.
- Для behaviour changes предпочитай добавлять или обновлять тесты.

## Системные проблемы и границы правила
- Если ошибка повторяется или указывает на системный дефект, фиксируй решение в подходящем месте: Memory Bank, rule, skill или документации.
- Для глубокой отладки используй skill `systematic-debugging`.
- Для security-critical задач используй skill `owasp-security`.
- Это правило задаёт baseline качества кода, а не заменяет специализированные security/debugging workflows.


# Rule: 07-project-workflow.md
# Правила работы с проектами пользователя

## Технический стек и инфраструктура
> 📁 Подробная информация: **`tech-stack.md`** (в той же папке Rules)
> MUST читать `tech-stack.md` при работе с сервером, деплоем, VPS или инфраструктурой.

**Кратко:** Python/FastAPI, Node.js/TypeScript, N8N, Claude API, Railway, Docker, PostgreSQL, Redis, Supabase, aiogram.

### 🚨 При создании нового сервиса — MUST обновить `tech-stack.md`

## .clineignore

- MUST добавлять `.clineignore` в каждый новый проект.
- Без `.clineignore` Cline загружает слишком много лишнего контекста.
- Используй шаблоны из `~/Documents/Cline/Templates/` по стеку проекта.
- Файлы из `.clineignore` можно явно подтянуть через `@path/to/file`, если они реально нужны в задаче.

## При старте нового проекта
1. MUST проверить, есть ли уже файлы проекта в рабочей директории.
2. MUST изучить README.md и другие `*.md` файлы с описанием.
3. SHOULD уточнить недостающие требования, если без них нельзя безопасно спроектировать решение.
4. MUST определить канонический project label для текущей сессии. Если существует `.clinerules/{project-name}.md`, используй имя этого файла как основной идентификатор проекта в формате `Проект: {project-name}.md`.
5. MUST создать текущий исполнимый чек-лист в `task_progress`.
6. Для длинной / multi-phase задачи MUST создать или обновить канонический global plan в `implementation_plan.md`, `docs/plan.md` или аналогичном plan file.
7. SHOULD предложить создать Memory Bank через `initialize memory bank`.
8. SHOULD создать `cline_docs/project-state.md`, если задача предполагает длительную работу, handoff или несколько этапов.
9. MUST один раз предложить создать **workspace rule / local trust** в `.clinerules/{project-name}.md` для нового проекта, если проект будет накапливать локальный trust-контекст, артефакты, continuity или project-specific knowledge. Если такого файла ещё нет, MUST явно предложить его создать.
10. При Supabase — MUST проверить `.env` на `SUPABASE_URL` и `SUPABASE_ANON_KEY`.

## Project header / project identity
- В первом содержательном ответе нового task, resume, audit, status update или после compaction MUST сначала писать строку `Проект: ...`, а сразу под ней — progress bar Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`, и только потом основной отчёт.
- Если существует workspace rule `.clinerules/{project-name}.md`, имя этого файла SHOULD быть каноническим project label.
- Если workspace rule отсутствует, агент MUST явно предложить создать его и до этого использовать временный project label, не теряя фокус на проекте.
- `implementation_plan.md`, `cline_docs/project-state.md`, `cline_docs/handoff-summary.md`, handoff / summary / resume docs SHOULD иметь вверху единый project block: строку `Проект: ...`, затем строку `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- При обновлении continuity-документов агент MUST сохранять этот project block и обновлять вместе с остальным статусом не только имя проекта, но и текстовый progress bar / фазу.
- Для project status/update/planning ответов после project block MUST использовать 3 слоя: `Что строим глобально` → `Средний план` → `Чек-лист`.
- В слое `Что строим глобально` MUST кратко фиксировать конечную цель проекта; если цель ещё не определена, агент MUST сначала предложить и согласовать её с пользователем.
- В слое `Средний план` MUST кратко описывать текущий блок / фазу: что именно делаем сейчас.
- В слое `Чек-лист` MUST давать декомпозицию ближайших исполнимых действий в формате Markdown checklist, пригодном для Cline.

## Project progress bar standard
- Канонический визуальный формат после строки `Проект: ...` = Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Процент может быть приблизительным инженерным ориентиром, а не псевдо-точной метрикой; он должен честно отражать стадию проекта.
- Короткая фаза после процента должна описывать текущий этап в 2–5 словах: например `runtime integration`, `regression`, `handoff cleanup`, `planning`.
- Если проект только начат, допустимы низкие значения вроде `10–20%`; если идёт финализация, допустимы `80–95%`; не ставить `100%`, пока definition of done реально не закрыт.

## Workspace rule / local trust
- Для нового проекта MUST один раз предложить создать workspace rule / local trust в `.clinerules/{project-name}.md`.
- Такой файл SHOULD хранить:
  - имя проекта;
  - цель и краткую архитектурную рамку;
  - что уже подтверждено live;
  - ключевые артефакты и где они лежат;
  - continuity docs и порядок чтения для следующей сессии;
  - ограничения, risks и what-is-not-confirmed.
- Workspace rule / local trust = локальный source of truth по проекту и trust-layer внутри workspace.
- Он дополняет `implementation_plan.md`, `cline_docs/project-state.md` и `cline_docs/handoff-summary.md`, а не заменяет их.

## При продолжении проекта
1. MUST прочитать `memory-bank/activeContext.md` и `memory-bank/progress.md`, если папка существует.
2. MUST прочитать `implementation_plan.md` или другой канонический plan file, если задача длинная / многоэтапная.
3. MUST прочитать `cline_docs/project-state.md`, если файл существует.

# Правила использования инструментов

## Завершение задач
### Доведение чек-листа до конца
- Если задача ведётся по `task_progress`, агент MUST считать её незавершённой, пока не выполнены все пункты чек-листа или пока пользователь явно не остановит/переформулирует задачу.
- Агент MUST не прерывать рабочий процесс и не делать вид, что задача завершена, если в чек-листе остаются незакрытые пункты.
- Если часть работы уже выполнена, но checklist ещё не закрыт, следующий ответ должен продолжать выполнение следующего релевантного шага, а не останавливаться на промежуточном статусе.
- `attempt_completion` использовать только когда весь актуальный checklist действительно закрыт, либо когда есть явный blocker, честно объяснённый пользователю.

- Используй `attempt_completion` только когда задача действительно завершена и результат можно внятно отдать пользователю.
- Не используй `attempt_completion` для обычных ответов, уточнений или короткого диалога.
- Не завершай задачу, если изменения не проверены в достаточной мере для текущего типа работы.
- Не передавай в `attempt_completion.command` команды, которые открывают или перезагружают редактор, если пользователь явно этого не просил.

## Когда что выбирать
- Используй `/smol`, если хочешь сохранить текущий task и убрать шум длинной истории.
- Используй `/newtask`, если началась новая тема, накопился нерелевантный контекст или нужен чистый handoff.
- Используй `/deep-planning`, если задача сложная, рискованная или требует архитектурного плана до правок.
- Используй `/newrule`, если ошибка или паттерн повторяются и это уже стоит закрепить в rules.
- Используй `/explain-changes`, если нужно быстро объяснить уже сделанный diff вместо ручного пересказа.
- Используй `/reportbug`, если проблема связана с поведением агента, инструмента или интеграции, а не с кодом проекта.

## Антипаттерны
- Не держи одну длинную сессию для несвязанных задач.
- Не завершай задачу формально, если по сути продолжается рабочий диалог.
- Не используй slash-команды без понятной цели для текущего workflow.
- Не ломай текущую сессию командами, которые открывают или перезапускают editor tooling без запроса пользователя.
- Не создавай новое правило или workflow для единичной случайной ошибки без повторяющегося паттерна.

## Project header discipline
- В первом user-facing ответе нового task, resume, handoff-recovery или после compaction MUST сначала указывать строку `Проект: ...`, а следующей строкой — progress bar Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Для long-task status/update/report ответов project block (`Проект: ...` + `Завершённость: [███████████░░░] 80% — <короткая фаза>`) SHOULD идти перед секциями `Короткий вывод`, `Что проверено` и остальным содержимым.
- Если project header неясен, агент MUST сначала проверить workspace rule, `implementation_plan.md`, `cline_docs/project-state.md` и `cline_docs/handoff-summary.md`, а уже потом отвечать.
- Если workspace rule для проекта отсутствует, агент MUST один раз предложить создать `.clinerules/{project-name}.md`.
- Для project-oriented ответов после project block SHOULD использоваться краткий 3-слойный формат: `Что строим глобально` → `Средний план` → `Чек-лист`.
- Не заменяй этим форматом весь ответ на длинную теорию: держи каждый слой коротким и operational.

## Project progress bar standard
- Канонический визуальный формат после строки `Проект: ...` = Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Процент может быть приблизительным инженерным ориентиром, а не псевдо-точной метрикой; он должен честно отражать стадию проекта.
- Короткая фаза после процента должна описывать текущий этап в 2–5 словах: например `runtime integration`, `regression`, `handoff cleanup`, `planning`.
- Если проект только начат, допустимы низкие значения вроде `10–20%`; если идёт финализация, допустимы `80–95%`; не ставить `100%`, пока definition of done реально не закрыт.

## Практика работы
- Для длинных задач предпочитай короткие рабочие циклы и чистые handoff’ы вместо бесконечного чата.
- Если история стала мешать качеству, сначала думай про `/smol` или `/newtask`, а не продолжай тащить шум.
- Используй встроенные команды как часть workflow, а не как случайные дополнительные функции.
- Если пользователь сообщает о проблеме в работе агента, не спорь с симптомом — направляй к `/reportbug` и кратко объясняй зачем это нужно.

## Практические уроки: как надо / как не надо

### Работа с файлами вне workspace
- **Как не надо:** пытаться создавать или патчить файлы вне текущего workspace через относительные пути вида `../.agents/...` в `apply_patch`, если инструмент ожидает работу внутри workspace. Это может привести к ошибкам уровня `EROFS: read-only file system, mkdir '/.agents'`.
- **Как надо:** для файлов вне workspace использовать абсолютные пути и безопасные системные операции (`execute_command`, Python/CLI запись файлов) вместо попытки протащить patch через относительный выход за пределы workspace.
- **Как думать:** если целевой путь лежит в `~/.agents/`, `~/Documents/Cline/` или другой глобальной директории пользователя, сначала считай это внешней по отношению к workspace областью и не полагайся на workspace-relative patching.

### Пополнение списка уроков
- Если найден устойчивый и повторяемый паттерн ошибки в использовании инструментов, SHOULD кратко фиксировать его в этом разделе в формате «Как не надо / Как надо».
- Не заносить сюда единичные случайные сбои без повторяемого паттерна.

## Авто-обучение на проверенных ошибках
- Если ошибка, неудачный ход или анти-паттерн были **исправлены и проверены**, агент SHOULD оценить, нужно ли зафиксировать урок в одном из слоёв знаний.
- Сначала MUST убедиться, что причина действительно понята, исправление проверено, а урок можно сформулировать коротко и без догадок.
- Дальше SHOULD выбрать правильный слой фиксации:
  - **Rule** — если это always-on policy, ограничение или общий принцип работы;
  - **Skill** — если это on-demand экспертиза, повторяемый workflow или domain pattern;
  - **Hook** — если нужна детерминированная автоматизация, блокировка или lifecycle enforcement;
  - **Workflow / script** — если это явная повторяемая последовательность действий;
  - **project-state / memory-bank / docs** — если знание project-specific и не должно становиться глобальным правилом.
- NEVER автоматически создавать новый skill или новый rule только потому, что произошёл один случайный сбой.
- Для фиксации урока SHOULD использовать минимальный полезный формат: **что было не так → как правильно → по какому сигналу распознавать кейс в будущем**.
- После фиксации урока SHOULD проверить, не дублирует ли он существующие Rules, Skills, Hooks или project notes.


## Длинные и объёмные задачи
- Для больших задач MUST сначала создавать канонический глобальный план в файле проекта (`implementation_plan.md`, `docs/plan.md` или аналогичном), а не полагаться только на Focus Chain.
- Для длинных задач MUST мыслить в 3 слоя:
  1. **Глобальный план** — master plan проекта.
  2. **Средний план** — operational plan текущей фазы.
  3. **Точечный чек-лист** — текущий исполнимый slice.
- Если в проекте есть `implementation_plan.md`, он MUST считаться canonical global plan / master checklist длинной задачи.
- `implementation_plan.md` SHOULD содержать цель, scope / non-scope, текущее состояние, ограничения, фазы, зависимости, definition of done и risks, а не список микро-действий.
- Если в проекте есть `cline_docs/project-state.md`, он MUST считаться canonical medium plan / operational state: текущая фаза, уже сделано, следующий точный шаг, ключевые решения, modified files, risks/blockers.
- `cline_docs/project-state.md` SHOULD также фиксировать, что уже подтверждено, что ещё не подтверждено, вход/выход текущей фазы и ближайшую проверку.
- `implementation_plan.md` и `cline_docs/project-state.md` вместе SHOULD считаться основным source of truth для long-task continuity; Focus Chain не должен считаться master plan.
- Focus Chain SHOULD использоваться как короткий оперативный список текущей фазы, а не как единственный source of truth для длинного проекта.
- `task_progress` MUST использоваться только для текущей фазы или ближайшего исполнимого среза; туда нельзя пихать весь большой master checklist длинного проекта.
- `task_progress` SHOULD обычно содержать 3–6 конкретных исполнимых пунктов и завершаться шагом проверки результата.
- Если задача длинная, multi-file или multi-phase, SHOULD начинать с `/deep-planning`, затем выполнять реализацию в новом или чистом task, опираясь на сохранённый plan file.
- Для длинных execution-фаз SHOULD дробить работу на фазы и использовать `/newtask` между крупными этапами, если история стала тяжёлой или изменилась фаза работы.
- Для маленьких задач допустимо пропустить отдельный master plan и ограничиться средним планом + `task_progress`, если риск низкий и зависимостей мало.
- После restore / resume / compaction MUST учитывать, что Focus Chain UI, markdown-файл и внутренняя task state могут расходиться; при конфликте source of truth = `implementation_plan.md` + `cline_docs/project-state.md`, а не только Focus Chain.
- Если вручную редактируется Focus Chain markdown, MUST помнить, что последующие обновления `task_progress` могут перезаписать этот список.
- Если Focus Chain мешает длинной задаче, допустимо временно отключить его или увеличить reminder interval, но это не заменяет канонические файлы проекта.
- Если наблюдается повторяемый рассинхрон Focus Chain / restore / task state, SHOULD рекомендовать пользователю `/reportbug`, а не пытаться лечить это только промптом.

## Поведение при высоком context usage
- Начиная примерно с `70%` context usage / progress bar, держи ответы короче и более операционными.
- Предпочитай summaries вместо сырых логов.
- Цитируй только минимальный объём доказательств, нужный для решения.
- Не вставляй большие куски файлов, если достаточно краткой выжимки или точечного excerpt.
- Перед тяжёлыми командами, широким поиском или большими чтениями файлов сначала думай про `/smol` / `/compact`.

## Safety behavior near context limits
- Не жди, пока контекст почти исчерпан.
- Делай compaction раньше, а не после деградации качества.
- Около `90%` context usage приоритетом становится сохранение контекста, а не скорость работы.
- В критической зоне не выполняй тяжёлые действия до compaction, если они не являются строго необходимыми.


# Rule: 09-skills-management.md
# Управление навыками (Skills Management)

## Правила использования Skills
- MUST проверять доступные skills перед сложной задачей.
- MUST использовать `use_skill()`, когда задача явно соответствует существующему skill.
- NEVER угадывать syntax, API или workflow, если есть релевантный skill.
- Глобальные Skills: `~/.agents/skills/`
- Проектные Skills: `.agents/skills/` внутри проекта

## Когда использовать skill
- Когда нужна специализированная domain-логика, которая не должна быть always-on.
- Когда задача требует повторяемого workflow, сложной процедуры или глубоких best practices.
- Когда подробные инструкции, примеры или scripts были бы слишком тяжёлыми для rules.

## Когда НЕ использовать skill
- Когда правило должно работать всегда и относится к базовому поведению агента.
- Когда задача слишком мала, чтобы загружать отдельный skill.
- Когда достаточно existing rule, workflow или hook без дополнительного on-demand слоя.
- Не создавай skill для единичной случайной ситуации без повторяющегося паттерна.

## Как выбирать слой
- **Rules** — always-on guidance, базовые ограничения, поведение и стандарты.
- **Skills** — on-demand экспертиза, глубокие workflow, best practices, references и scripts.
- **Workflows** — явные повторяемые последовательности действий, запускаемые вручную.
- **Hooks** — детерминированная автоматизация и enforcement в lifecycle-событиях.

## Формат файла SKILL.md
- Каждый skill MUST начинаться с YAML frontmatter.
- Минимум: `name` и `description`.
- Для сложных skills SHOULD использовать `examples/`, `templates/`, `scripts/` или дополнительные docs.

- Rules routing MUST ссылаться только на skills, доступные в активном system registry, а не просто существующие на диске.

- Если UI-задача затрагивает кастомные виджеты, keyboard/focus behavior, forms или accessibility, routing должен вести не только в UI skill, но и к official accessibility/pattern docs, а не к импровизации «по памяти».
- Для query-задач по Obsidian vault canonical routing сейчас: `obsidian-second-brain` + при необходимости `obsidian-second-brain-world`.
- Перед переводом local-only skill в общий routing нужно синхронизировать три слоя: папка skill → Rules routing → system registry.

- Предлагай новый skill, если паттерн повторяется 3+ раза и не должен жить в always-on rules.
- Перед созданием нового skill проверь, не покрывается ли задача существующим skill, workflow или hook.
- Новый skill должен давать реальную повторяемую ценность: domain depth, workflow, patterns, scripts или проверяемые примеры.
- Файл: `~/.agents/skills/<skill-name>/SKILL.md`
- Перед добавлением нового skill согласуй это с пользователем.
- Для создания, обновления и оценки новых skills используй skill `skill-authoring`, если задача именно про authoring/evolution skills.

## Эволюция системы через Rules + Skills
- Если найден повторяемый и устойчивый паттерн, агент SHOULD оценить, где он должен жить: Rule, Skill, Hook, Workflow или project note.
- NEVER создавать новый skill только потому, что произошла одна случайная ошибка или был один единичный кейс.
- Новые skills должны появляться через осознанный отбор, а не через хаотичное накопление знаний.
- Если создаётся новый skill, проверь, нужен ли короткий routing update в Rules, чтобы Rules и Skills не расходились.
- Если после ошибки или неудачного решения появился **проверенный и повторяемый урок**, сначала классифицируй его как Rule / Skill / Hook / Workflow / project note и только потом создавай новый артефакт.
- Если lesson candidate тянет на новый или обновлённый skill, SHOULD использовать `skill-authoring` как канонический процесс authoring/evolution.


# Rule: 10-hooks-management.md
# Управление хуками (Hooks Management)

> 📁 Полная документация, шаблоны и примеры — в скилле `hooks-management`.
> MUST использовать `use_skill("hooks-management")` при создании или отладке хуков.

## Расположение
- **Глобальные**: `~/Documents/Cline/Hooks/` — для всех проектов
- **Проектные**: `.clinerules/hooks/` — только для конкретного проекта

## Установленные хуки

| Хук | Назначение |
|---|---|
| `TaskStart` | Логирует начало задачи, добавляет timestamp в контекст |
| `TaskComplete` | Отправляет уведомление в Telegram |
| `PreToolUse` | Блокирует .js в TS-проектах, защищает от `rm -rf /`, блокирует `git add .env` |
| `PostToolUse` | Логирует метрики в `~/Documents/Cline/Logs/tool-usage.log` |

## Когда использовать hooks
- Используй hooks для детерминированной автоматизации, валидации, policy enforcement и логирования.
- Используй hooks, когда действие должно происходить автоматически и без пропусков.
- Не используй hooks для гибкой логики, длинных рассуждений или редких workflow — для этого есть rules, skills и workflows.

## Базовые правила
- MUST возвращать валидный JSON в stdout.
- MUST логировать в stderr (`>&2`), не в stdout.
- SHOULD делать hooks быстрыми, минимальными и предсказуемыми.
- NEVER блокировать операции без веской причины, особенно в `PreToolUse`.
- Для сложной логики hook-ов, шаблонов и debugging используй skill `hooks-management`.

## Границы и ограничения
- Hooks — это enforcement layer, а не замена rules, skills и workflows.
- Блокирующие hooks должны срабатывать только на high-confidence и high-risk случаях.
- Если hook начинает мешать обычной работе чаще, чем предотвращает реальную проблему, его нужно упростить или пересмотреть.
- `Notification` не работает в VS Code — используй `Stop` там, где нужна реакция по завершению.

## Routing note для context / continuity hooks
- Для context/continuity hook architecture source of truth должен жить не только в самом hook-коде, но и в runbook / workspace note.
- Если hooks обслуживают continuity, telemetry и compaction recovery, держи краткий summary в workspace note, а подробную operational схему — в runbook.
- Если рабочая hook-система ушла дальше общего правила, обнови routing note или ссылку на runbook, чтобы Rules не отставали от runtime.


# Rule: 11-browser-automation.md
# Автоматизация браузера (Browser Automation)

> 📁 Полная документация, паттерны и примеры — в скилле `browser-automation`.
> MUST использовать `use_skill("browser-automation")` при сложных задачах с браузером.

## Когда использовать браузер
- Используй Playwright для интерактива: клики, формы, логин, модалки, dropdown, drag & drop, вкладки, редиректы и JS-поведение.
- Используй Playwright для диагностики: консольные ошибки, сетевые запросы, нестабильные состояния UI и реальные шаги пользователя.
- Для сложных браузерных задач, e2e-сценариев и UI-диагностики используй skill `browser-automation`.

## Playwright vs Tavily

| Задача | Инструмент |
|---|---|
| Просто прочитать страницу | `tavily_extract` |
| Скриншот страницы | Playwright |
| Клики, формы, интерактив | Playwright |
| Консоль/сетевые запросы | Playwright |
| Сбор данных с сайта | Playwright или `tavily_crawl` |
| Проверить структуру интерфейса | Playwright (`browser_snapshot`) |
| Авторизация + действия | Playwright |

## Основные инструменты

```
browser_navigate         — перейти по URL
browser_snapshot         — получить accessibility-снапшот страницы
browser_take_screenshot  — сделать скриншот (PNG/JPEG)
browser_click            — кликнуть по элементу (по ref из snapshot)
browser_type             — ввести текст в поле
browser_fill_form        — заполнить несколько полей сразу
browser_press_key        — нажать клавишу
browser_wait_for         — ждать текст или его исчезновение
browser_console_messages — прочитать консоль (error/warning/info)
browser_network_requests — посмотреть сетевые запросы
browser_evaluate         — выполнить JS на странице
browser_close            — закрыть страницу
browser_navigate_back    — назад
browser_tabs             — список/создание/выбор вкладок
browser_hover            — навести мышь
browser_select_option    — выбрать в dropdown
browser_handle_dialog    — принять/отклонить диалог
```

## Правила использования
- MUST использовать `browser_snapshot` вместо screenshot для навигации — он даёт структуру страницы и `ref` для кликов.
- MUST всегда закрывать браузер через `browser_close` после завершения задачи.
- MUST проверять `browser_console_messages` после действий, связанных с UI и логикой страницы.
- MUST использовать `browser_wait_for` после навигации и значимых действий, а не кликать цепочкой без проверки состояния.
- MUST после изменения DOM или перехода страницы при необходимости вызывать `browser_snapshot` заново — старые `ref` могут устареть.
- SHOULD проверять user-visible результат действия, а не только факт клика.
- SHOULD использовать `browser_network_requests` при диагностике 4xx/5xx, загрузки данных и странного поведения клиента.
- SHOULD использовать `browser_fill_form` для заполнения нескольких полей — быстрее чем по одному.
- SHOULD делать `browser_take_screenshot` при обнаружении визуальных проблем.
- NEVER открывать реальные банки, финансы и личные аккаунты через Playwright без явного запроса пользователя.

## Безопасность и границы
- Playwright открывает изолированный браузер без данных пользователя.
- НЕ использовать расширение Chrome для Claude.
- Не выполняй через браузер рискованные пользовательские действия без явного разрешения.
- При работе с авторизацией используй данные только через переменные окружения.

## Быстрый старт
```
browser_navigate → browser_snapshot → browser_click(ref) → browser_console_messages
```


# Rule: 12-headless-mode.md
# Headless режим (Cline CLI)

> 📁 Полная документация, опции и cron-примеры — в скилле `headless-mode`.
> MUST использовать `use_skill("headless-mode")` при настройке автономных задач или запуске Cline на VPS.

## Когда использовать headless
- Используй headless режим для повторяемых, ограниченных и проверяемых задач.
- Используй его для cron-задач, регулярных отчётов, batch-проверок, массовых правок и автоматизированных проверок.
- Перед переводом задачи в headless режим сначала добейся, чтобы она стабильно работала вручную.

## Когда НЕ использовать headless
- Не используй headless режим для плохо определённых, рискованных или широких задач.
- Не используй его там, где нужен частый human-in-the-loop, уточнения или ручной review после каждого шага.
- Не запускай опасные и необратимые действия без явного ограничения scope и таймаута.
- Не используй headless как замену workflows и hooks, если задача требует детерминированной последовательности или lifecycle enforcement.

## Базовые правила
- MUST использовать headless/auto-approve режим только вместе с таймаутом.
- MUST явно задавать рабочую директорию или контекст запуска.
- MUST делать задачу узкой и проверяемой, а не расплывчатой.
- MUST предусматривать способ проверки результата: через history, логи, diff, артефакты или follow-up проверку.
- SHOULD сначала прогонять задачу вручную, затем автоматизировать её.
- NEVER запускать опасные команды без таймаута и понятных границ.

## Границы правила
- Это правило задаёт policy для автономного запуска Cline CLI, а не заменяет skill `headless-mode`.
- За конкретными флагами, cron-примерами и VPS-командами обращайся к skill `headless-mode`.
- Если задача больше похожа на automation workflow, lifecycle automation или hook orchestration, сначала оцени, не лучше ли подойдут workflows, hooks или skill `hooks-management`.
- Для крупных автономных сценариев с несколькими параллельными ветками оцени, не нужен ли skill `parallel-work`.


# Rule: 13-parallel-work.md
# Параллельная работа (Parallel Work)

> 📁 Полная документация, примеры и контракты — в скилле `parallel-work`.
> MUST использовать `use_skill("parallel-work")` при сложных задачах требующих параллельного выполнения.

## Когда использовать параллельную работу
- Используй параллельную работу, когда задачу можно разделить на независимые или слабо связанные подзадачи.
- Используй её для широкого исследования кодовой базы, сравнения подходов и изолированной параллельной работы над кодом.
- Не параллель задачи, где каждый следующий шаг напрямую зависит от результата предыдущего, если зависимость не зафиксирована явно.

## Выбор подхода

| Подход | Когда использовать |
|---|---|
| **Sub-агенты** | Параллельное исследование, чтение файлов, сбор фактов и сравнение гипотез |
| **Git worktrees** | Изолированная параллельная работа с кодом, отдельные ветки и рискованные изменения |
| **Headless (VPS)** | Регулярные фоновые задачи по расписанию |

## Правила использования use_subagents

🚨 **Критические правила (проверено тестами):**

- MUST передавать `prompt_1` как отдельный XML-параметр — NEVER оставлять пустым
- Sub-агенты **НЕ имеют доступа к MCP** (Tavily, GitHub, Railway и т.д.)
- Sub-агенты имеют только: `read_file`, `list_files`, `search_files`, `list_code_definition_names`, `execute_command`, `use_skill`
- `execute_command` — только read-only: `ls`, `grep`, `git log`, `git diff`
- SHOULD запрашивать структурированный вывод (JSON) для удобной обработки результатов
- При ошибке файла — агент сообщает об ошибке и продолжает (не падает весь запуск)
- Каждый агент работает независимо — не видит результаты других агентов
- Sub-агенты должны возвращать **сжатые резюме** (1000-2000 токенов), не полные данные
- NEVER воспринимай результат sub-агента как финальный без проверки и синтеза.

### Рабочие паттерны

**Параллельное чтение файлов:**
```
prompt_1: "Прочитай файл X и верни [что именно нужно]"
prompt_2: "Прочитай файл Y и верни [что именно нужно]"
```

**Параллельное выполнение команд:**
```
prompt_1: "Выполни команду: [команда] и верни результат"
prompt_2: "Выполни команду: [команда] и верни результат"
```

**Структурированный вывод:**
```
prompt_1: "Прочитай файл X и верни JSON: {\"key\": \"...\", \"count\": 0}"
```

### Что НЕ работает в sub-агентах
- ❌ `tavily_search`, `tavily_extract`
- ❌ `github search_code`, `get_file_contents`
- ❌ `railway deploy`, `n8n-mcp` и другие MCP инструменты
- ✅ Только локальные файловые операции + read-only CLI + `use_skill`

### Лимиты
- Максимальный ответ: ~45,000 символов — при превышении таймаут → сужай scope, дроби задачу или возвращай более короткое резюме
- Баг: `--thinking` у родителя → HTTP 400 у sub-агентов → отключить `--thinking`

## Правила для worktrees
- Используй worktrees, когда параллельные задачи затрагивают код, а не только исследование.
- MUST давать worktree понятное имя по задаче или ветке.
- MUST удалять worktree после завершения задачи.
- SHOULD проверять отсутствие незакоммиченных изменений перед удалением.
- Не запускай параллельную работу в worktrees по одним и тем же файлам без явного плана координации.

## Контракты и синтез
- MUST определять контракт между агентами до запуска: кто что делает, какие входы использует и какой результат возвращает.
- MUST запускать upstream-агентов первыми, если другие подзадачи зависят от их результата.
- После параллельной фазы MUST выполнить синтез: сравнить выводы, убрать конфликты, выбрать итоговый путь.
- NEVER принимать «я закончил» без проверки результата, зависимости и совместимости с общей задачей.
- Перед удалением worktree SHOULD убедиться, что изменения либо закоммичены, либо явно не нужны.

## Границы и антипаттерны
- Не используй параллельную работу ради параллельной работы — overhead должен окупаться.
- Не смешивай исследование и кодовые изменения в одном и том же subagent-потоке.
- Не параллель задачи с плотной общей зависимостью без явного orchestration-плана.
- Если задача лучше решается одной чистой сессией, не дроби её искусственно.


# Rule: 15-plan-mode-limitations.md
# Ограничения PLAN MODE

## Что недоступно в PLAN MODE
- В PLAN MODE нельзя изменять файлы, запускать команды, выполнять MCP-инструменты и делать другие actions, требующие ACT MODE.
- PLAN MODE предназначен для исследования, чтения файлов, поиска, вопросов и проектирования решения.

## Что делать в PLAN MODE
- Используй `read_file`, `list_files`, `search_files` и другие read-only инструменты для сбора контекста.
- Используй поиск и документацию, если нужно добрать достоверность до реализации.
- Формируй конкретный план действий до начала изменений.
- Для проектных, архитектурных, multi-file и длинных задач SHOULD формировать план в 3 слоя:
  1. **Глобальный план** — цель, scope / non-scope, фазы, зависимости, definition of done и risks.
  2. **Средний план** — текущая фаза, 3–7 шагов внутри неё, проверка и следующий точный шаг.
  3. **Точечный чек-лист** — тот ближайший исполнимый slice, который потом перейдёт в `task_progress` после перехода в ACT MODE.
- В user-facing ответе PLAN MODE для project-задачи SHOULD показывать эти 3 слоя в кратком формате: `Что строим глобально` → `Средний план` → `Чек-лист`.
- Если глобальная цель проекта ещё не зафиксирована, PLAN MODE SHOULD сначала предложить её и согласовать с пользователем, а уже потом детализировать средний план и чек-лист.
- Для длинных задач SHOULD явно указывать, где будет жить каждый слой: `implementation_plan.md` / `docs/plan.md` для master plan, `cline_docs/project-state.md` для operational state, `task_progress` для текущего slice.
- MUST не смешивать уровни плана: не выдавать микро-чек-лист за master plan и не сводить весь проект к одному списку действий.
- Если требования неясны и это влияет на точность решения, задай уточняющий вопрос.

## Переход в ACT MODE
- Если для выполнения задачи нужны изменения файлов, команды, MCP или реальные действия, явно попроси пользователя переключиться в ACT MODE.
- Используй прямую формулировку: `Переключись на ACT MODE чтобы я мог выполнить изменения.`
- Не делай вид, что можешь завершить реализацию в PLAN MODE.

## Границы режима
- PLAN MODE — для исследования и планирования.
- ACT MODE — для реализации и проверки результата.
- Не путай план, предположение или архитектурную идею с реально выполненной работой.

# Rule: 16-ai-agent-collaboration.md
# Взаимодействие с ИИ Агентами

## Когда использовать
- Используй взаимодействие с другим агентом, когда у него есть локальный контекст, доступ или окружение, которого нет у тебя.
- Используй его для настройки удалённых сервисов, проверки конфигурации, выполнения задач в чужом runtime и делегирования автономной работы.
- Не используй внешний агент, если задачу проще и безопаснее решить локально без лишнего orchestration.

## Когда НЕ использовать
- Не делегируй задачу внешнему агенту, если она требует постоянного back-and-forth, плотного общего контекста или чувствительных ручных решений на каждом шаге.
- Не используй внешний агент как замену `parallel-work`, если достаточно sub-агентов или worktrees внутри текущей среды.
- Не отправляй во внешний агент секреты, токены и чувствительные данные без явной необходимости и понятной модели доверия.

## Доверие и границы доступа
- Перед делегированием выясни, в каком окружении работает агент, какие у него есть инструменты, доступ и ограничения.
- Считай внешний агент отдельной доверительной зоной, а не продолжением своей локальной среды.
- Не проси внешний агент выполнять рискованные или необратимые действия без явного scope и возможности проверки результата.

## Базовый протокол взаимодействия
1. Сначала узнай, что агент умеет, какие у него есть инструменты, доступ и ограничения.
2. Коротко объясни, кто ты, в каком контексте работаешь и зачем делегируешь задачу.
3. Дай агенту конкретную, ограниченную и проверяемую задачу.
4. Запроси результат в проверяемом формате: что изменено, что проверено, какие ограничения остались.
5. После ответа отдельно проверь результат, а не принимай его на веру.

## Практически подтверждённый smoke-test паттерн
- Для удалённого Cline CLI сначала делай **capability discovery**, а уже потом делегируй задачу.
- Для безопасных проверок используй **read-only контракт**: явно запрети изменения, сеть и рискованные команды.
- Для чистого smoke test используй **новый `userId` или `newChat`**, чтобы не тащить старый контекст и память прошлой задачи.
- После ответа удалённого агента делай **локальную перепроверку тех же фактов** в его runtime или через независимый канал.
- Если wrapper/API возвращает `taskId`, `exitCode`, `result`, `stderr`, используй их как часть контракта и не считай задачу успешной только по тексту `result`.

## Что реально подтверждено на VPS Cline CLI
- Подход `локальный агент → HTTP wrapper → удалённый Cline CLI` реально работает.
- Capability discovery проходит успешно, и агент может честно вернуть ограничения и степень уверенности.
- Read-only делегированная проверка файлов и версий проходит успешно при явном контракте на JSON-ответ.
- Локальная verification loop обязательна и реально полезна: она подтвердила факты удалённого ответа.
- Память сессии влияет на поведение, поэтому для тестов и диагностики безопаснее использовать изолированный `userId` или новый чат.
- Документации и старым заметкам про удалённый агент доверять недостаточно: фактическую версию CLI, ограничения и поведение нужно перепроверять live.

## Паттерн: агент → агент
```
Локальный агент
    ↓ формулирует задачу и контракт
Удалённый/внешний агент
    ↓ выполняет задачу в своём окружении
    ↓ возвращает результат и ограничения
Локальный агент
    ↓ проверяет, принимает или дорабатывает
```

## Правила взаимодействия
- MUST объяснять, кто ты и зачем обращаешься к другому агенту.
- MUST давать конкретные задачи с явным ожидаемым результатом.
- MUST проверять результат отдельно после ответа агента.
- MUST для smoke tests и диагностики использовать изолированный контекст (`newChat`, отдельный `userId` или эквивалент), если у удалённого агента есть память между сессиями.
- SHOULD сначала спрашивать, что агент может сделать сам, а что нет.
- SHOULD задавать контракт: входы, выходы, критерий успеха, ограничения.
- SHOULD просить структурированный ответ, предпочтительно JSON, если результат потом будет перепроверяться автоматически.
- NEVER принимать «всё готово» без верификации.
- NEVER настраивать вручную то, что агент может надёжно сделать сам в собственном окружении.

## Границы и routing
- Для локальной параллельной работы и sub-агентов используй `parallel-work`.
- Для OpenClaw-специфичных задач используй skill `openclaw`.
- Для внешнего агентного взаимодействия через wrapper/API сначала оцени доверие, доступ и стоимость координации.
- Если задача превращается в orchestration нескольких агентов, сначала зафиксируй роли, контракты и точку синтеза результата.

## Каноничный гибридный подход
- `mcp-obsidian` в текущем setup — это read/search слой, а не write API.
- Все записи и обновления в vault должны делаться обычными файловыми инструментами.
- Предпочитай структуру `raw/`, `wiki/`, `output/`.
- Для совместимости с текущим MCP не используй hidden source folders вроде `.raw/`, если хочешь читать их через MCP.

## Каноничные core files
- `wiki/hot.md` — читать первым для восстановления контекста.
- `wiki/index.md` — читать вторым как карту страниц.
- `wiki/overview.md` — high-level карта знаний.
- `wiki/meta/current-focus.md` — текущие приоритеты и активные нити.
- `wiki/log.md` — журнал значимых операций.

## Continuity contract
- `cline_docs/project-state.md` = continuity по текущей задаче.
- `wiki/hot.md` = continuity по knowledge base.
- `wiki/meta/current-focus.md` = operational focus внутри второго мозга.
- Перекладывай результат из task-layer в vault только через осознанный save-back workflow.

## Каноничный порядок чтения
1. `wiki/hot.md`
2. `wiki/index.md`
3. `wiki/overview.md`
4. `wiki/meta/current-focus.md` при релевантности
5. 3–5 конкретных страниц
6. source summaries
7. raw — только как last resort

## Работа с MCP
- Для `read_notes` используй относительные пути (`raw/file.md`, `wiki/index.md`).
- Если vault расположен в symlink path на macOS (например `/tmp`), для MCP-конфига и тестов предпочитай `realpath`.
- Не ожидай от `search_notes` полнотекстового поиска по содержимому — это поиск по именам заметок.
- `search_notes` ищет по имени файла, а не по `title` во frontmatter или body note.
- Для `search_notes` предпочитай короткие частичные запросы (`pricing`, `obsidian`, `inbox`), а не длинные точные фразы из заголовка.
- Если нужен content-level поиск, сначала используй `wiki/index.md` / `wiki/hot.md` / targeted reads или обычный файловый поиск.

## Soft automation policy
- Hooks в second brain workflow должны быть soft reminders, а не auto-write слой.
- После изменений в `wiki/` и `raw/` допустимы мягкие напоминания обновить `wiki/hot.md` и при необходимости `wiki/meta/current-focus.md`.
- Не делай слепую автоматическую синхронизацию между `project-state.md` и vault continuity файлами.

## Inbox / processed policy
- Новые материалы по умолчанию клади в `raw/inbox/`.
- После ingest переводи их в `raw/processed/` или явно фиксируй, что source уже обработан.
- Legacy файлы в корне `raw/` допустимы, но не превращай корень `raw/` в постоянную свалку.

## Review / approve policy
- Для крупных save-back или ingest-изменений используй промежуточный слой `output/review/`.
- Маленькие и безопасные правки можно вносить прямо в live wiki.
- Если структура спорная, сначала review, потом перенос в `wiki/`.

## Live save-back policy
- После **реальной аналитической сессии** сначала сохраняй decision-ready knowledge artifacts, а не сырой transcript.
- Нормальный save-back по живому кейсу обычно включает: 1 главный артефакт (`question` или `comparison`), 1–2 supporting updates и обновление continuity-файлов.
- Если по итогам живой сессии обнаружились устаревшие или вымышленные ссылки, сначала приведи live knowledge layer в честное состояние, а потом обновляй `hot.md` и `current-focus.md`.
- Не создавай новый source summary только потому, что хочется «полноты»; новый внешний source нужен под реальный operational gap.

## Lint scope policy
- При lint различай **live knowledge layer** и template layer.
- Placeholder-ссылки в `CLAUDE.md` и `*_template.md` не считай broken links live-слоя, если это явно шаблонные маркеры.
- Broken links в knowledge pages, index drift и stale continuity — это реальные дефекты и высокий приоритет.
- После framework-level save-back или серии значимых knowledge updates делай lint-pass и фиксируй, что было auto-fixed, а что остаётся manual.

## Entity / graph policy
- Для полезного graph view сначала усиливай `wiki/entities/`, `wiki/concepts/`, synthesis pages и `[[wikilinks]]`.
- Graph View в Obsidian — это следствие хорошей структуры, а не причина её делать.
- Не тащи graph DB, ontology-first architecture или тяжёлый RAG, пока entity layer ещё слабый.
- Если хочется «графы потом», сначала делай connected entities, connected concepts и hub pages.

## Operational cadence
- После каждой реальной аналитической сессии делай save-back в тот же рабочий цикл.
- После серии значимых обновлений или новой framework-level страницы прогоняй lint.
- `wiki/hot.md` обновляй при смене реального operational focus, а не после каждой мелкой правки.
- `wiki/meta/current-focus.md` держи коротким и action-oriented: приоритеты, open threads, next useful reads.

## Когда НЕ переусложнять
- Не добавляй autoresearch, scheduled agents, canvas и фоновую автоматизацию до тех пор, пока не заработал core-loop: scaffold → ingest → query → save → world → lint.
- Не читай весь vault подряд без narrowing через `hot.md` и `index.md`.
- Не дублируй страницы, если можно обновить существующие.

## SessionStart restore
- Если текущий workspace сам является second brain vault, SessionStart может подтягивать `wiki/hot.md` и `wiki/meta/current-focus.md` как lightweight continuity.
- Не загружай весь vault автоматически на старте; хватит hot/focus слоя.

## Compaction hygiene
- PreCompact / SessionStart restore для второго мозга должны быть workspace-aware: marker после compaction нельзя применять к другому workspace.
- Если marker принадлежит другому workspace, SessionStart должен его игнорировать, а не потреблять.

- **Использование**: Прямое API для загрузки файлов (Google Drive), таблиц (Google Sheets), отправки почты (Gmail) и т.д. БЕЗ сборки вебхуков в визуальном конструкторе. 
- Мы не создаем визуальный Webhook, мы просто кидаем POST-запросы напрямую в Google Drive API через шлюз Maton.ai!

## Правила парсинга и логирования Судебного Кабинета (Sud KZ)
- **Формат логов (Единый Google Doc)**: Логи успешного скачивания пишутся в ЕДИНЫЙ Google Документ: https://docs.google.com/document/d/1QtjId5qF4zhqHog8sqTQi97biTXnjTQZ7huJpv8GBLQ/edit?usp=sharing (Журнал скачивания судебных дел).
- **Содержание логов для каждого дела (Проверяемость)**:
  1. Скриншот: зашел на страницу, вбил поиск.
  2. Скриншот: зашел в дело.
  3. Факт скачивания документа.
  4. Ссылка на скачанный файл на Google Диске.
  5. Ссылка на оригинал (Судебный кабинет/источник).

## Правило генерации Veo (Озвучка)
- При отправке текста для генерации озвучки через Veo **ВСЕГДА убирай тире (—) и дефисы (-)** из текста промпта. Они вызывают артефакты в речи (заикания, повторы, переозвучивание).


## 📊 Правило логирования, биллинга и авторизации (Supabase)
- **ИНТЕГРАЦИЯ**: Все новые API эндпоинты и MCP инструменты должны быть обернуты в проверку API-ключа через Supabase.
- **ЛОГИРОВАНИЕ**: Каждый вызов должен сохраняться в таблицу `api_logs` (user_id, endpoint, payload).
- **БИЛЛИНГ**: Перед выполнением тяжелых задач (например, парсинг суд.кз), бэкенд обязан проверить баланс `tokens_balance` в таблице `users`.
- **ДЕТАЛИ**: Полная схема базы данных и архитектура описана в `docs/learn/system_architecture.md`.

## Безопасность при стриминге
- Никогда не выводи пароли, ключи API и другие секретные данные открытым текстом в интерфейс команд (run_command и др.), если пользователь ведет стрим или попросил скрыть их. Используй динамическое чтение из .env файла через bash-переменные, чтобы в интерфейсе отображался только скрипт чтения, а не сам пароль.

## Генерация видео (Veo 3.1 / Seedance 2.0)
- **ОБЯЗАТЕЛЬНО:** Всегда вшивать русскую озвучку/реплики персонажей прямо внутрь текстового видео-промпта (в кавычках), если не сказано иное. Генераторы используют этот текст для нативного липсинка и генерации звука.
- **Пример:** `The character yells "Макс, спасай!" and runs.`

## Правило загрузки видео/файлов на сервер (YouTube, Google Drive)
- При любой загрузке файлов/видео на сторонние площадки (YouTube, Google Drive и т.д.) через скрипты, ОБЯЗАТЕЛЬНО извлекать дату создания и дату изменения оригинального файла на диске компьютера.
- Эти даты необходимо добавлять в описание (description) видео или файла при загрузке.
