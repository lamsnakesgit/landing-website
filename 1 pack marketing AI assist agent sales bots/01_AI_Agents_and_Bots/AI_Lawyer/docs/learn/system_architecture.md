# 🧠 Архитектура Второго Мозга и MCP/OpenAPI Интеграций

Этот документ создан для того, чтобы зафиксировать базовые принципы нашей разработки и не терять контекст между сессиями разных ИИ-агентов (Antigravity, Cline, Cursor, Claude Code).

---

## 1. Концепция Second Brain (Второй Мозг)

### Почему агенты "забывают" контекст?
Каждый раз, когда ты открываешь новый чат с ИИ, его контекстное окно (память) абсолютно пустое. Агент не знает, о чем вы штурмили вчера.

### Решение: Obsidian Second Brain
Мы используем подход, при котором вся память выгружается в локальные Markdown-файлы (`.md`) в единую папку (Vault).
- **Планы и идеи** сохраняются в папку `docs/learn/` или `docs/architecture/`.
- **Перед началом работы** любой локальный агент обязан прочитать `PROGRESS.md` или сделать запрос к Second Brain через MCP-инструменты.
- **В конце работы** (после успешного спринта 15-20 минут) агент автоматически вызывает скрипты сохранения контекста и делает `git commit`.

Таким образом, разработка становится непрерывной. Ты можешь написать идею с телефона (через Obsidian Sync или iCloud), а когда придешь домой, локальный агент сразу возьмет её в работу.

## 2. Разница между MCP и OpenAPI (Custom Connectors)

### Для Десктопных Агентов (Cline, Cursor, Claude Desktop) 👉 MCP
**MCP (Model Context Protocol)** — это современный протокол связи, созданный специально для локальных ИИ-приложений.
- Работает по SSE (Server-Sent Events) или stdio.
- **Не требует сложной OAuth-авторизации.**
- Наша ссылка: `https://mcp-151-244-228-104.nip.io/sse`

### Для Браузерных Агентов (ChatGPT, Claude Web) 👉 OpenAPI (Swagger)
Браузерные интерфейсы не понимают MCP напрямую. Им нужен стандартный REST API с документацией формата OpenAPI.
- Требует описания всех эндпоинтов (JSON схема).
- Поддерживает стандартные методы авторизации (API Key, OAuth2).
- Наша ссылка: `https://api-151-244-228-104.nip.io/openapi.json`

Если ты сидишь в браузере (Claude Web) и пытаешься подключить Custom Connector — вставляй OpenAPI-ссылку!

## 3. Архитектура Логирования, Биллинга и Авторизации (Supabase)

Чтобы проект можно было дать "на тест" другим людям (или продавать по подписке), мы внедряем централизованную базу данных на базе **Supabase**.

### Схема данных (Data Schema):
1. **Таблица `users`**:
   - `id` (UUID)
   - `telegram_id` (Integer)
   - `api_key` (String, уникальный токен пользователя)
   - `subscription_tier` (String: "free", "pro")
   - `tokens_balance` (Integer)

2. **Таблица `api_logs`**:
   - `id` (UUID)
   - `user_id` (Foreign Key -> users.id)
   - `endpoint` (String, например `/api/v1/cases/search`)
   - `request_payload` (JSONB)
   - `response_status` (Integer)
   - `created_at` (Timestamp)

### Как это работает:
1. Когда сторонний пользователь делает запрос к нашему API (через браузерного Клода или сторонний софт), он передает свой `API Key` в заголовке `Authorization`.
2. Наш бэкенд (`app.py` или `web_mcp.py`) делает запрос в Supabase: проверяет баланс токенов и уровень подписки.
3. Если баланс положительный, бэкенд выполняет поиск по базе судебных дел.
4. После ответа бэкенд записывает лог в таблицу `api_logs` и списывает токены с `users`.

> **ПРАВИЛО ДЛЯ АГЕНТОВ**: Любые новые инструменты или эндпоинты должны оборачиваться в декораторы/middleware, которые логируют запросы в Supabase!
