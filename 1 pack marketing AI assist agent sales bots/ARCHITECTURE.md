# Architecture Decisions (Архитектурные решения)

Данный документ описывает архитектуру системы ежедневной автоматической лидогенерации и B2B-outreach продаж.

## 📊 Общая схема пайплайна

Система построена на принципах устойчивости к блокировкам (anti-bot bypass), экономичности (GPT-4o-mini) и фокуса на генерацию выручки (revenue generation) за счет создания высококонверсионных персонализированных коммерческих предложений.

## 🛠️ Компоненты системы

1. **Скрапер (Playwright)** (`scripts/playwright_leadgen.py`):
   - Запускает Chromium с флагами обхода детекции автоматизации (`AutomationControlled`).
   - Ищет вакансии по ключевым словам ("ии", "разработка ботов", "автоматизация", "crm", "маркетинг", "контекстная реклама", "ии контент") на hh.ru/hh.kz.
   - Ищет авторов/профили на threads.net через DuckDuckGo HTML-поиск.
   - Обогащает компании с `hh.kz` контактами (БИН, телефон, email) с `adata.kz` путем прямого поиска названия ТОО/ИП.
   - Сохраняет результаты в промежуточные JSON файлы.

2. **ИИ-Обогатитель (OpenAI mini)** (`06_Scripts_and_Tools/daily_leadgen.py`):
   - Загружает сырые лиды из JSON файлов.
   - Формирует системный промпт (в стиле Ника Сараева) для генерации боли компании, угла захода, списка того, что мы можем им предложить, и текста первого сообщения.
   - Применяет эвристики и оценивает соответствие лида (AI Score 1-10).
   - Сортирует лидов по оценке, выводя самые горячие наверх.

3. **Хранилище и Результаты**:
   - Локально: CSV-файл `leads_summary.csv` и структурированный отчет `leads_report.md` в папке `03_Marketing_and_Sales/daily_leads/{date_str}/`.
   - Внутренние карточки: для каждого лида в папке `details/` создается отдельный Markdown-файл с драфтом первого сообщения и предложением, что позволяет менеджеру по продажам за 1 клик скопировать готовое персонализированное сообщение.
   - База данных: запись лидов в Supabase (таблица `leads`) для ведения истории и исключения дублей.

4. **Интеграция с Telegram**:
   - Отправка ежедневного сводного отчета.
   - Поочередная отправка ТОП-5 самых горячих лидов с контактами прямо в чат с готовой кнопкой/текстом первого сообщения для быстрой отправки.

5. **Управление запуском и устойчивость процессов (Scheduler & Signal Handling)**:
   - **Служба расписания**: Для запуска используется единственный агент macOS `launchd` с идентификатором `com.higherpower.daily_leadgen` (запуск каждый день в 09:00 по местному времени).
   - **Служба гарантированного запуска (RunAtLoad)**: plist-файл планировщика настроен с параметром `<key>RunAtLoad</key><true/>`. Это гарантирует, что если в 09:00 утра компьютер был выключен или спал, сбор запустится автоматически при первом входе пользователя в сессию Aqua.
   - **Защита от дублирования запусков**: Чтобы предотвратить повторный сбор данных при последующих входах или перезагрузках в течение одного дня, в оркестратор `run_pipeline.py` внедрена логика проверки даты последнего запуска по маркеру `logs/.last_run`. Скрипт проверяет дату и моментально завершает работу (exit 0) с закрытием окна терминала, если сегодня сбор уже выполнялся. Принудительный запуск возможен через аргумент `--force`.
   - **Слой изоляции TCC**: Чтобы обойти блокировки macOS TCC при доступе к Рабочему столу (`Desktop`), `launchd` запускает обертку `/Users/higherpower/run_daily_pipeline_wrapper.sh` через `osascript`.
   - **Устойчивость к закрытию терминала**:
     - В скриптах `run_pipeline.py`, `playwright_leadgen.py` и `daily_leadgen.py` настроено игнорирование сигнала `SIGHUP` (через `signal.SIG_IGN`).
     - В `run_pipeline.py` перехватываются исключения `BrokenPipeError` и `OSError` при записи в stdout.
     - Благодаря этому, если пользователь закрывает окно Терминала, открытое планировщиком, фоновые Python-процессы продолжают сбор и обогащение лидов в фоновом режиме, успешно доводя выполнение до конца и отправляя финальный отчет.

## 💰 Экономическая целесообразность (Revenue Generating)

- **Почему мы это делаем?** Поиск и квалификация лидов вручную занимает от 2 до 3 часов в день у высокооплачиваемого сейлз-менеджера или основателя. Автоматизация этого процесса снижает затраты времени до 5 минут в день (только на отправку готовых сообщений).
- **Экономичность**: Использование модели `gpt-4o-mini` стоит доли цента за один лид, при этом качество генерации офферов остается премиальным.
- **Масштабируемость**: Пайплайн легко интегрируется с n8n или планировщиками на Mac/VPS, работая автономно 365 дней в году.

## 🤖 Архитектура ИИ-Ассистента (WhatsApp + Content Factory)

Система взаимодействия с пользователями строится по **модульному принципу**, разделяя "общение" и "тяжелую генерацию контента".

### 1. Главный Ассистент (Оркестратор / Роутер)
- **Роль:** Принимает все входящие запросы от пользователя/клиента и решает, какому специализированному саб-агенту делегировать задачу.
- **Инструменты:** Вызывает саб-агентов как инструменты (Tools), передавая им текстовые инструкции. Не содержит в себе сложных API-подключений.

### 2. WhatsApp Agent (Коммуникатор)
- **Интеграция:** Evolution API (через MCP сервер).
- **Роль:** Отвечает исключительно за чтение чатов, поиск контактов и подготовку сообщений к отправке. Содержит логику защиты (HITL) перед финальной отправкой.

### 3. Контент-Завод (Carousel Agent)
- **Проблема:** Если зашить логику сложных каруселей, промптинга для Nano Banana 2 и генерации структуры Hook->Agitation->Solution в главного ассистента, это приведет к путанице контекста и галлюцинациям.
- **Решение:** Контент-завод реализуется как **отдельный независимый саб-агент**.
- **Связь:** Главный ассистент вызывает тул `order_content_factory(topic, media_files)`, ждет результат (готовые картинки/URL) и передает их дальше.

### 4. Notion Agent (База Знаний и CRM)
- **Интеграция:** Notion MCP Server.
- **Роль:** Отвечает за сохранение лидов, поиск инструкций, ведение заметок и выгрузку данных из базы знаний.
- **Связь:** Если клиент спрашивает сложные технические детали услуги, Оркестратор просит Notion Агента: *"Найди в базе знаний прайс и условия"*. Если появился новый лид, Оркестратор говорит: *"Сохрани Ивана в CRM Notion"*.

### 3. Инфраструктура: Docker vs PM2
Для запуска MCP-сервера WhatsApp на VPS выбран **Docker**, а не PM2.
- **Почему Docker безопаснее:** Он создает изолированную файловую систему и сеть. Если в коде стороннего MCP-сервера есть уязвимость, злоумышленник не получит доступ к корневой системе VPS (где лежат ключи в `.env`).
- **Почему Docker стабильнее:** Он "капсулирует" все зависимости (версию Node.js, npm пакеты). Это исключает проблему "у меня на локалке работало, а на VPS сломалось из-за другой версии Node".
- *PM2* быстрее в первоначальном запуске для простых скриптов, но для сетевых "мостов" вроде MCP, которые "смотрят" наружу, Docker — это индустриальный стандарт.

## 🧠 Стратегия Multi-Agent Development & Handoffs

Управление проектом, где код пишут ИИ-агенты (Antigravity, Cline, Cursor), требует строгой дисциплины, иначе контекст теряется, а код превращается в хаос.

### Эффективное управление агентами:
1. **Разделение ролей (Separation of Concerns):**
   - Не заставляйте одного агента делать всё. Создайте специализированных агентов.
   - *Пример:* Один агент (N8N Architect) занимается только воркфлоу n8n. Другой (Backend) пишет MCP-сервер на TypeScript. Третий занимается фронтендом.
2. **Context Handoffs (Передача контекста):**
   - Как только окно контекста забивается (>50%), текущий агент ОБЯЗАН остановиться и создать/обновить артефакт `HANDOFF.md` или `PROGRESS.md`.
   - В файле должно быть: *Что сделано -> В каком файле мы остановились -> Какие ошибки не решены -> Что должен сделать следующий агент.*
3. **Использование кастомных скиллов (Skills/Tools):**
   - Если вы нашли удачный промпт или скрипт (например, пайплайн Nanoமைப்பு Banana), упакуйте его в папку `.agents/skills/`. Следующий агент автоматически прочитает этот `SKILL.md` и поймет, как с этим работать.
4. **Docs as Code:**
   - Вся архитектура, API ключи (примеры), порты и логика должны быть задокументированы в `ARCHITECTURE.md`. Новый агент начинает работу с прочтения этого файла.

## ⚖️ Архитектура ИИ-Юриста (Интеграция с Судебным Кабинетом)

Проект ИИ-Юриста (AI Lawyer) требует автоматизированного доступа к Судебному кабинету (office.sud.kz) для сбора данных (например, парсинг трудовых споров для RAG).

### Проблема классического парсинга (Playwright)
Изначально была попытка автоматизировать авторизацию через Playwright + локально запущенный NCALayer (Java). Данный подход оказался крайне хрупким, нестабильным (периодически падал NCALayer, менялись порты websocket, отваливались коннекты) и требовал ручного участия пользователя, что вызвало негативный опыт.

### Текущее Решение: Native C-Bindings (KalkanCrypt)
- **Полный отказ от GUI и NCALayer:** Для авторизации используется официальная C-библиотека от НУЦ РК (`libkalkancryptwr-64.so.2.0.2`), работающая напрямую с файлами сертификатов (`GOST...p12`).
- **Слой изоляции (Docker / AlmaLinux 8):** Поскольку библиотека KalkanCrypt скомпилирована под старые стандарты и вызывает Segmentation Fault (SIGSEGV) из-за конфликта OpenSSL в новых версиях Ubuntu (24.04), был выбран путь запуска библиотеки внутри изолированного Docker-контейнера на базе `almalinux:8`.
- **Компиляция зависимостей:** В контейнере предварительно собирается `libiconv` (GNU) и устанавливается `pcsc-lite`, которые необходимы для работы `KalkanCrypt`.
- **Python Wrapper (`ctypes`):** Скрипт `auth_kalkan.py` подгружает `.so` файл через `ctypes.CDLL(..., mode=ctypes.RTLD_GLOBAL)`. Инициализация криптопровайдера происходит через вызов функции `KC_LoadKeyStore`, после чего формируется валидная XML-подпись для авторизации в Судебном кабинете.
- **Интеграция с парсером:** Подписанный XML передается в `parser_tk.py`, который совершает фоновые HTTP-запросы и выкачивает судебные акты для последующей векторизации и добавления в RAG-базу.
