# Local Code Search

**Статус: ПРОВЕРЕНО** — smoke test пройден 2026-03-28.

Семантический поиск по локальному коду через MCP `github.com/cocoindex-io/cocoindex-code`.
Используй вместо grep и ручного перебора файлов.

## Подтверждённые факты
- Бинарник: `$HOME/.local/bin/ccc`
- Версия пакета: `cocoindex-code v0.2.10`
- Smoke test: `ccc search 'MCP server search tool' --limit 3` → 3 результата, скоры 0.568–0.613
- Индекс репо cocoindex-code: 347 чанков, 35 файлов (python/markdown/toml/bash)
- Формат вывода: `--- Result N (score: X.XXX) --- / File: path:lines [lang] / <код>`
- `ccc init` создаёт `~/.cocoindex_code/global_settings.yml` и `<project>/.cocoindex_code/settings.yml`
- `ccc status` показывает chunks/files/languages breakdown

## Когда использовать
- репозиторий > 20–30 файлов
- незнакомая кодовая база
- нужно найти бизнес-логику по смыслу
- `search_files` даёт слишком много шума
- нужно быстро войти в проект

## Когда НЕ использовать
- знаешь точное имя файла/функции — используй `read_file`
- проект маленький (< 10 файлов) — `search_files` будет быстрее
- нужен exact match строки — используй `search_files` с regex
- индекс ещё не создан в этом проекте (нужно сначала `ccc init` + `ccc index`)

## Паттерн использования

```
1. сформулируй запрос на естественном языке
2. вызови MCP tool search(query="...", limit=5)
3. открой только 1–3 самых релевантных файла через read_file
4. уточни запрос если нашлось нерелевантное
5. только потом вноси правки
```

## Примеры запросов

**Telegram / боты:**
- «где обрабатывается входящий webhook от telegram»
- «как валидируется telegram initData»
- «где отправляются сообщения пользователю»

**N8N / автоматизация:**
- «где создаётся n8n workflow»
- «как настраивается HTTP Request нода»
- «где хранятся credentials для n8n»

**API / сервисы:**
- «как устроен retry для HTTP запросов»
- «где происходит валидация входных данных»
- «как настроен CORS»

**LiteLLM / AI:**
- «где настраивается routing между моделями»
- «как работает fallback для провайдеров»
- «где логируются запросы к LLM»

**Docker / деплой:**
- «где настраивается docker-compose»
- «как происходит деплой на Railway»
- «где определяются переменные окружения»

## Первый запуск в проекте (один раз)

```bash
export PATH="$HOME/.local/bin:$PATH"
cd /путь/к/проекту
ccc init   # создаёт settings.yml (~мгновенно)
ccc index  # строит индекс (1–5 мин для среднего репо)
ccc status # проверяем: chunks/files/languages
```

После этого поиск через MCP работает без задержек.

## Проверка статуса

export PATH="$HOME/.local/bin:$PATH"

## Комбинированный паттерн с parallel-work

Для больших репо и параллельного исследования:
1. semantic search — найти 5–10 релевантных файлов
2. передать список файлов sub-агентам
3. каждый sub-агент читает свой кусок и возвращает резюме

## Ограничения
- требует первичной инициализации (`ccc init` + `ccc index`) в каждом проекте
- первый `ccc index` тяжёлый (загрузка модели torch, несколько минут)
- последующие запросы быстрые (daemon остаётся в памяти)
- индекс автоматически обновляется при изменении файлов
- `PATH` должен включать `$HOME/.local/bin` для доступа к `ccc`

## Диагностика проблем

```bash
ccc doctor   # проверка настроек, daemon, модели, файлов, индекса
ccc daemon status  # статус фонового daemon
ccc daemon restart # перезапуск если завис
```
