# Skill Authoring

Этот skill нужен, когда надо **создать, обновить или отрефакторить другой skill** без превращения системы в свалку из дублирующих навыков.

## Главный принцип
Создавай новый skill **не потому что что-то узнал**, а потому что появился **повторяемый и устойчивый паттерн**, который:
- уже не должен жить в always-on rules;
- слишком тяжёл для короткой rule-инструкции;
- будет реально полезен в будущих сессиях;
- не покрывается существующим skill / hook / workflow / project note.

## Когда использовать
- нужно создать новый skill с нуля;
- нужно обновить существующий skill после нескольких повторяющихся ошибок;
- нужно понять, что делать с новым знанием: Rule, Skill, Hook, Workflow или project note;
- нужно превратить повторяемый workflow в reusable skill;
- нужно навести порядок в skill, который разросся, дублирует rules или конфликтует с другими skills.

## Когда НЕ использовать
- это единичная ошибка или единичный кейс;
- достаточно короткого обновления в Rules;
- это lifecycle automation, которую лучше решать через Hooks;
- это разовая проектная заметка, которую лучше хранить в `cline_docs/`, `memory-bank/` или `docs/`;
- уже есть существующий skill, который покрывает задачу без существенных пробелов.

## Decision tree: куда должно жить новое знание

### 1. Rule
Выбирай Rule, если инструкция должна работать **всегда**.

Примеры:
- язык ответов;
- базовые требования безопасности;
- policy по поиску документации;
- always-on routing уровня «для X используй skill Y».

### 2. Skill
Выбирай Skill, если нужна **on-demand экспертиза**:
- повторяемый workflow;
- domain-specific best practices;
- проверяемая процедура с шагами, примерами и анти-паттернами;
- то, что не нужно тащить в every-session context.

### 3. Hook
Выбирай Hook, если это должно происходить **детерминированно автоматически**:
- блокировка опасной операции;
- логирование;
- context injection в lifecycle event;
- автоматический checkpoint / restore.

### 4. Workflow / command / script
Выбирай Workflow, если нужна **явная повторяемая последовательность действий**, запускаемая вручную.

### 5. Project note / docs / memory-bank
Выбирай заметку или docs, если это:
- локальный incident log;
- source of truth по конкретному проекту;
- handoff / project-state / audit summary;
- материал, который не должен автоматически маршрутизироваться как экспертиза.

## Workflow создания или обновления skill

### Шаг 1. Проверка повтора
Подтверди, что паттерн реально повторяется.

Минимальный порог:
- желательно 3+ повторения;
- или один очень дорогой и системный класс ошибок, который точно повторится.

### Шаг 2. Проверка overlap
Перед созданием нового skill обязательно проверь:
- нет ли уже существующего skill с тем же назначением;
- не лучше ли обновить старый skill;
- не лучше ли решить это через Rule / Hook / Workflow.

### Шаг 3. Формулировка trigger-description
Описание skill должно быть написано так, чтобы skill легко маршрутизировался.

Правила:
- коротко;
- конкретно;
- с явным **when to use**;
- без пересказа всего workflow;
- с ключевыми словами реальных пользовательских запросов.

### Шаг 4. Минимальное ядро SKILL.md
Оставляй в `SKILL.md` только:
- назначение;
- когда использовать;
- когда не использовать;
- decision points;
- основной workflow;
- smoke tests;
- red flags.

Тяжёлые детали выноси в:
- `docs/`
- `templates/`
- `scripts/`
- `examples/`

## Каноническая структура skill

```text
<skill-name>/
├── SKILL.md
├── docs/
├── templates/
├── scripts/
└── examples/
```

Необязательно создавать всё сразу. Начинай минимально.

## Канонический шаблон SKILL.md

```md
---
name: your-skill-name
description: Use when ...
---

# Your Skill Name

Коротко: что делает skill и какую проблему решает.

## Когда использовать
- ...

## Когда НЕ использовать
- ...

## Workflow
1. ...
2. ...
3. ...

## Smoke tests
- Запрос 1 → ожидаемое поведение
- Запрос 2 → ожидаемое поведение

## Red flags
- ...
```

## Правила качества skill
- один skill = одна зона ответственности;
- не дублируй always-on rules;
- не храни секреты;
- не превращай skill в wiki или dump-файл;
- не делай skill слишком общим, если его невозможно корректно маршрутизировать;
- лучше короткий skill + ссылки на bundled files, чем длинная простыня;
- если skill уже слишком раздут, сначала подумай про split/refactor.

## Red flags — skill создавать не надо
- «агент однажды ошибся»;
- «хочу сохранить случайную мысль»;
- «можно просто дописать 3 строки в Rule»;
- «это проектная заметка, а не reusable capability»;
- «этот skill будет пересекаться с уже существующим почти 1-в-1».

## Обязательная связь с Rules
Если создан новый skill, проверь:
1. нужен ли короткий routing update в Rules;
2. не появился ли конфликт с существующими Rules;
3. не нужно ли обновить `09-skills-management.md` или другой routing rule.

Skill не должен жить изолированно от Rules.

## Smoke tests для skill-authoring

### Smoke test 1 — Rule vs Skill
Запрос:
> «Мы уже третий раз чиним один и тот же workflow. Нужно ли делать новый skill?»

Ожидание:
- skill сначала проверяет repeatability;
- потом отличает Skill от Rule / Hook / note;
- потом предлагает осмысленное решение.

### Smoke test 2 — update existing skill
Запрос:
> «Есть existing skill, но он стал слишком длинным и начал дублировать docs. Как его переделать?»

Ожидание:
- skill предлагает shrink core + вынести тяжёлые материалы в bundled files.

### Smoke test 3 — nonsense prevention
Запрос:
> «Создай новый skill на основе одной случайной ошибки.»

Ожидание:
- skill останавливает мусорогенерацию;
- предлагает Rule / note / incident log вместо нового skill.

## Финальная политика
Эволюция через Rules + Skills должна быть:
- не хаотичной;
- не мусорящей контекст;
- не плодящей дубли;
- а превращающей реально повторяемые знания в reusable capabilities.

Если сомневаешься — **сначала не создавай skill**, а проверь, не лучше ли Rule, Hook, Workflow или project note.
