# Context Management & Memory Bank

## Управление контекстом
- Следи за чистотой контекста: длинная и нерелевантная история ухудшает качество решений.
- Используй `/smol` (alias: `/compact`), если нужно сжать текущую задачу без смены контекста работы.
- Используй `/newtask`, если задача сменилась, контекст перегружен или нужен чистый handoff.
- Auto-Compact считай фоновой страховкой, а не заменой осмысленного управления памятью.
- Если видишь `context usage` / `context window progress` / progress bar около `70%`, считай это ранним порогом compaction.
- Если видишь `context usage` / `context window progress` / progress bar около `90%`, считай это критическим порогом и приоритетом для срочного compaction.

## Пороги compaction
- `70%` — ранний порог compaction.
- `90%` — критический аварийный порог.

## Поведение на 70%
- Перед крупным чтением, широким поиском, grep, build, test run, рефакторингом или multi-file edit сначала инициируй `/smol` / `/compact`.
- После compaction продолжай только с минимального следующего полезного шага.
- Предпочитай узкие чтения файлов, точечный поиск и инкрементальные правки.
- Не подтягивай большие логи и большие сгенерированные файлы без строгой необходимости.

## Поведение на 90%
- Немедленно останавливай несущественную работу.
- Срочно инициируй `/smol` / `/compact` до любых следующих тяжёлых действий.
- Не запускай heavy commands, broad scans, длинные тестовые прогоны и большие чтения файлов до compaction.
- Не продолжай обычное выполнение задачи, пока compaction не завершён.

## Если compaction не помог
- Если контекст остаётся высоким после compaction или задача меняет фазу, используй `/newtask`.
- В handoff переноси только: текущую цель, уже принятые решения, изменённые файлы, оставшиеся следующие шаги и blockers / risks.
- Не тащи в новый task шумные логи, тупиковые попытки и дублирующуюся историю.

## Project identity in continuity
- В первом содержательном ответе нового task, resume, compaction-recovery или handoff MUST явно указывать текущий проект строкой `Проект: <workspace-rule-file.md>` или `Проект: <project-name>`, а следующей строкой — текстовый progress bar в формате Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Если в workspace есть `.clinerules/{project-name}.md`, его имя файла SHOULD быть каноническим project label для статусов, handoff и continuity-ответов.
- Если workspace rule ещё не создан, MUST явно предложить создать его и до этого использовать временный project label в том же формате.
- `implementation_plan.md`, `cline_docs/project-state.md`, `cline_docs/handoff-summary.md` и аналогичные continuity-файлы SHOULD начинаться с блока из двух строк: сначала `Проект: ...`, затем `Завершённость: [███████████░░░] 80% — <короткая фаза>`, чтобы после compaction/resume было сразу видно, над чем идёт работа и где мы по прогрессу.

## Project progress bar standard
- Канонический визуальный формат после строки `Проект: ...` = Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Процент может быть приблизительным инженерным ориентиром, а не псевдо-точной метрикой; он должен честно отражать стадию проекта.
- Короткая фаза после процента должна описывать текущий этап в 2–5 словах: например `runtime integration`, `regression`, `handoff cleanup`, `planning`.
- Если проект только начат, допустимы низкие значения вроде `10–20%`; если идёт финализация, допустимы `80–95%`; не ставить `100%`, пока definition of done реально не закрыт.

## Memory Bank
- Если `memory-bank/` существует, при продолжении работы сначала читай `activeContext.md` и `progress.md`.
- `projectbrief.md`, `systemPatterns.md`, `techContext.md` и `productContext.md` читай только если задача требует архитектурного, доменного или технического контекста.
- Держи Memory Bank кратким и актуальным: это рабочая память проекта, а не архив всего подряд.
- Обновляй Memory Bank после значимых этапов, смены направления, перед handoff и перед длинной паузой.

## Project State
- Если существует `cline_docs/handoff-summary.md`, читай его сразу после `cline_docs/project-state.md`, особенно после compaction / resume / handoff.
- Для длинных задач `handoff-summary.md` SHOULD хранить короткую resume-выжимку: что уже подтверждено, где остановились, следующий точный шаг и важные operational notes.
- После compaction или восстановления сессии сначала перечитывай `project-state.md` + `handoff-summary.md`, а уже потом продолжай execution.
- Если существует `cline_docs/project-state.md`, используй его как оперативную выжимку по текущей задаче.
- Для длинных задач `cline_docs/project-state.md` SHOULD хранить: текущую фазу, уже сделано, следующий точный шаг, modified files, ключевые решения и risks/blockers.
- Если в проекте есть `implementation_plan.md` или аналогичный plan file, читай его вместе с `cline_docs/project-state.md`: plan file = master plan, project-state = оперативное состояние.
- При handoff, resume и compaction source of truth для long-task continuity = `implementation_plan.md` + `cline_docs/project-state.md`, а не только Focus Chain или память текущего task.
- Обновляй `project-state.md` после значимого прогресса, перед compaction и перед передачей задачи.
- Не обновляй state-файл бюрократически после каждого мелкого действия.

## Checkpoints и краткость
- Для длинных execution-задач предпочитай короткие, проверяемые slices вместо одной большой непрозрачной фазы.
- После каждого значимого slice SHOULD обновлять `cline_docs/project-state.md` и, если есть, `cline_docs/handoff-summary.md`, чтобы следующий resume не зависел от памяти текущего чата.
- Checkpoints сохраняют состояние кода; Memory Bank и project-state сохраняют знания и контекст.
- Если задача ушла в серию неудачных итераций или накопила много нерелевантной истории, предпочитай сжатие или новую задачу вместо раздувания текущей сессии.
- Держи memory-файлы короткими, конкретными и ориентированными на продолжение работы.

## Границы правила
- Это правило управляет памятью и контекстом, а не процессом разработки.
- Логику разбиения задач, подтверждений пользователя, workflow-шагов и commit cadence держи в отдельных process/workflow rules.
