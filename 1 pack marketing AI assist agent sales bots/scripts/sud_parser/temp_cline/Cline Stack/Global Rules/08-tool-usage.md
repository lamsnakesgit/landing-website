# Правила использования инструментов

## Завершение задач
### Доведение чек-листа до конца
- Если задача ведётся по `task_progress`, агент MUST считать её незавершённой, пока не выполнены все пункты чек-листа или пока пользователь явно не остановит/переформулирует задачу.
- Агент MUST не прерывать рабочий процесс и не делать вид, что задача завершена, если в чек-листе остаются незакрытые пункты.
- Если часть работы уже выполнена, но checklist ещё не закрыт, следующий ответ должен продолжать выполнение следующего релевантного шага, а не останавливаться на промежуточном статусе.
- `attempt_completion` использовать только когда весь актуальный checklist действительно закрыт, либо когда есть явный blocker, честно объяснённый пользователю.

- Используй `attempt_completion` только когда задача действительно завершена и результат можно внятно отдать пользователю.
- Не используй `attempt_completion` для обычных ответов, уточнений или короткого диалога.
- Не завершай задачу, если изменения не проверены в достаточной мере для текущего типа работы.
- Не передавай в `attempt_completion.command` команды, которые открывают или перезагружают редактор, если пользователь явно этого не просил.

## Slash-команды

| Команда | Когда использовать |
|---|---|
| `/smol` | Когда текущая задача остаётся той же, но историю нужно сжать |
| `/compact` | Алиас для `/smol`, используй в тех же сценариях |
| `/newtask` | Когда задача сменилась или контекст стал мешать качеству работы |
| `/deep-planning` | Перед сложными изменениями, затрагивающими несколько файлов или архитектуру |
| `/newrule` | Когда нужно создать новое правило интерактивно |
| `/explain-changes` | Когда нужно объяснить git diff или изменения |
| `/reportbug` | Когда пользователь сообщает о проблеме в работе агента или инструмента |

## Когда что выбирать
- Используй `/smol`, если хочешь сохранить текущий task и убрать шум длинной истории.
- Используй `/newtask`, если началась новая тема, накопился нерелевантный контекст или нужен чистый handoff.
- Используй `/deep-planning`, если задача сложная, рискованная или требует архитектурного плана до правок.
- Используй `/newrule`, если ошибка или паттерн повторяются и это уже стоит закрепить в rules.
- Используй `/explain-changes`, если нужно быстро объяснить уже сделанный diff вместо ручного пересказа.
- Используй `/reportbug`, если проблема связана с поведением агента, инструмента или интеграции, а не с кодом проекта.

## Антипаттерны
- Не держи одну длинную сессию для несвязанных задач.
- Не завершай задачу формально, если по сути продолжается рабочий диалог.
- Не используй slash-команды без понятной цели для текущего workflow.
- Не ломай текущую сессию командами, которые открывают или перезапускают editor tooling без запроса пользователя.
- Не создавай новое правило или workflow для единичной случайной ошибки без повторяющегося паттерна.

## Project header discipline
- В первом user-facing ответе нового task, resume, handoff-recovery или после compaction MUST сначала указывать строку `Проект: ...`, а следующей строкой — progress bar Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Для long-task status/update/report ответов project block (`Проект: ...` + `Завершённость: [███████████░░░] 80% — <короткая фаза>`) SHOULD идти перед секциями `Короткий вывод`, `Что проверено` и остальным содержимым.
- Если project header неясен, агент MUST сначала проверить workspace rule, `implementation_plan.md`, `cline_docs/project-state.md` и `cline_docs/handoff-summary.md`, а уже потом отвечать.
- Если workspace rule для проекта отсутствует, агент MUST один раз предложить создать `.clinerules/{project-name}.md`.
- Для project-oriented ответов после project block SHOULD использоваться краткий 3-слойный формат: `Что строим глобально` → `Средний план` → `Чек-лист`.
- Не заменяй этим форматом весь ответ на длинную теорию: держи каждый слой коротким и operational.

## Project progress bar standard
- Канонический визуальный формат после строки `Проект: ...` = Variant 3: `Завершённость: [███████████░░░] 80% — <короткая фаза>`.
- Процент может быть приблизительным инженерным ориентиром, а не псевдо-точной метрикой; он должен честно отражать стадию проекта.
- Короткая фаза после процента должна описывать текущий этап в 2–5 словах: например `runtime integration`, `regression`, `handoff cleanup`, `planning`.
- Если проект только начат, допустимы низкие значения вроде `10–20%`; если идёт финализация, допустимы `80–95%`; не ставить `100%`, пока definition of done реально не закрыт.

## Практика работы
- Для длинных задач предпочитай короткие рабочие циклы и чистые handoff’ы вместо бесконечного чата.
- Если история стала мешать качеству, сначала думай про `/smol` или `/newtask`, а не продолжай тащить шум.
- Используй встроенные команды как часть workflow, а не как случайные дополнительные функции.
- Если пользователь сообщает о проблеме в работе агента, не спорь с симптомом — направляй к `/reportbug` и кратко объясняй зачем это нужно.

## Практические уроки: как надо / как не надо

### Работа с файлами вне workspace
- **Как не надо:** пытаться создавать или патчить файлы вне текущего workspace через относительные пути вида `../.agents/...` в `apply_patch`, если инструмент ожидает работу внутри workspace. Это может привести к ошибкам уровня `EROFS: read-only file system, mkdir '/.agents'`.
- **Как надо:** для файлов вне workspace использовать абсолютные пути и безопасные системные операции (`execute_command`, Python/CLI запись файлов) вместо попытки протащить patch через относительный выход за пределы workspace.
- **Как думать:** если целевой путь лежит в `~/.agents/`, `~/Documents/Cline/` или другой глобальной директории пользователя, сначала считай это внешней по отношению к workspace областью и не полагайся на workspace-relative patching.

### Пополнение списка уроков
- Если найден устойчивый и повторяемый паттерн ошибки в использовании инструментов, SHOULD кратко фиксировать его в этом разделе в формате «Как не надо / Как надо».
- Не заносить сюда единичные случайные сбои без повторяемого паттерна.

## Авто-обучение на проверенных ошибках
- Если ошибка, неудачный ход или анти-паттерн были **исправлены и проверены**, агент SHOULD оценить, нужно ли зафиксировать урок в одном из слоёв знаний.
- Сначала MUST убедиться, что причина действительно понята, исправление проверено, а урок можно сформулировать коротко и без догадок.
- Дальше SHOULD выбрать правильный слой фиксации:
  - **Rule** — если это always-on policy, ограничение или общий принцип работы;
  - **Skill** — если это on-demand экспертиза, повторяемый workflow или domain pattern;
  - **Hook** — если нужна детерминированная автоматизация, блокировка или lifecycle enforcement;
  - **Workflow / script** — если это явная повторяемая последовательность действий;
  - **project-state / memory-bank / docs** — если знание project-specific и не должно становиться глобальным правилом.
- NEVER автоматически создавать новый skill или новый rule только потому, что произошёл один случайный сбой.
- Для фиксации урока SHOULD использовать минимальный полезный формат: **что было не так → как правильно → по какому сигналу распознавать кейс в будущем**.
- После фиксации урока SHOULD проверить, не дублирует ли он существующие Rules, Skills, Hooks или project notes.


## Длинные и объёмные задачи
- Для больших задач MUST сначала создавать канонический глобальный план в файле проекта (`implementation_plan.md`, `docs/plan.md` или аналогичном), а не полагаться только на Focus Chain.
- Для длинных задач MUST мыслить в 3 слоя:
  1. **Глобальный план** — master plan проекта.
  2. **Средний план** — operational plan текущей фазы.
  3. **Точечный чек-лист** — текущий исполнимый slice.
- Если в проекте есть `implementation_plan.md`, он MUST считаться canonical global plan / master checklist длинной задачи.
- `implementation_plan.md` SHOULD содержать цель, scope / non-scope, текущее состояние, ограничения, фазы, зависимости, definition of done и risks, а не список микро-действий.
- Если в проекте есть `cline_docs/project-state.md`, он MUST считаться canonical medium plan / operational state: текущая фаза, уже сделано, следующий точный шаг, ключевые решения, modified files, risks/blockers.
- `cline_docs/project-state.md` SHOULD также фиксировать, что уже подтверждено, что ещё не подтверждено, вход/выход текущей фазы и ближайшую проверку.
- `implementation_plan.md` и `cline_docs/project-state.md` вместе SHOULD считаться основным source of truth для long-task continuity; Focus Chain не должен считаться master plan.
- Focus Chain SHOULD использоваться как короткий оперативный список текущей фазы, а не как единственный source of truth для длинного проекта.
- `task_progress` MUST использоваться только для текущей фазы или ближайшего исполнимого среза; туда нельзя пихать весь большой master checklist длинного проекта.
- `task_progress` SHOULD обычно содержать 3–6 конкретных исполнимых пунктов и завершаться шагом проверки результата.
- Если задача длинная, multi-file или multi-phase, SHOULD начинать с `/deep-planning`, затем выполнять реализацию в новом или чистом task, опираясь на сохранённый plan file.
- Для длинных execution-фаз SHOULD дробить работу на фазы и использовать `/newtask` между крупными этапами, если история стала тяжёлой или изменилась фаза работы.
- Для маленьких задач допустимо пропустить отдельный master plan и ограничиться средним планом + `task_progress`, если риск низкий и зависимостей мало.
- После restore / resume / compaction MUST учитывать, что Focus Chain UI, markdown-файл и внутренняя task state могут расходиться; при конфликте source of truth = `implementation_plan.md` + `cline_docs/project-state.md`, а не только Focus Chain.
- Если вручную редактируется Focus Chain markdown, MUST помнить, что последующие обновления `task_progress` могут перезаписать этот список.
- Если Focus Chain мешает длинной задаче, допустимо временно отключить его или увеличить reminder interval, но это не заменяет канонические файлы проекта.
- Если наблюдается повторяемый рассинхрон Focus Chain / restore / task state, SHOULD рекомендовать пользователю `/reportbug`, а не пытаться лечить это только промптом.

## Поведение при высоком context usage
- Начиная примерно с `70%` context usage / progress bar, держи ответы короче и более операционными.
- Предпочитай summaries вместо сырых логов.
- Цитируй только минимальный объём доказательств, нужный для решения.
- Не вставляй большие куски файлов, если достаточно краткой выжимки или точечного excerpt.
- Перед тяжёлыми командами, широким поиском или большими чтениями файлов сначала думай про `/smol` / `/compact`.

## Safety behavior near context limits
- Не жди, пока контекст почти исчерпан.
- Делай compaction раньше, а не после деградации качества.
- Около `90%` context usage приоритетом становится сохранение контекста, а не скорость работы.
- В критической зоне не выполняй тяжёлые действия до compaction, если они не являются строго необходимыми.
